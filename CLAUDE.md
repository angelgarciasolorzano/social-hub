## Project Overview

**social-hub** is a Laravel 13 + React 19 SPA (Inertia v3) social-media application. Domain code is split into modules; most follow the project's controller/model/provider/request/resource/route layout. **Modules are moving to `app/Modules/<Domain>/` (SOC-38)**: Post, Comment and Like have moved, as has the special system module Admin for the Filament panel and authorization (SOC-44); ActivityLog was born there (SOC-54), and so was Announcement (SOC-61). The migration is incremental; the other domains still live at `app/<Domain>/` (the *old architecture*) until their own tasks move them. The `app/<Domain>/Modules/<Feature>/` submodule layout described below for Auth and User also belongs to the old architecture (e.g. Auth → `app/Modules/Auth/`); don't confuse it with the top-level `app/Modules/` folder, which holds migrated modules. Anything outside it (`app/Providers/`, `app/Http/`, `app/Events/`, `app/Console/`, `app/Support/`, global listeners, policies, middleware, etc.) is global application code unless it belongs to an old-architecture domain.

Domains in this codebase:

- **Auth** (`app/Auth/`) — login, register, email verification, password reset (via Fortify), the login 2FA challenge, and trusted devices.
  - **Feature layout**: Login, Register, Email verification, Password, and TrustedDevice live under `app/Auth/Modules/{Login,Register,Email,Password,TrustedDevice}/`. Each feature owns its applicable controllers, requests, services, listeners, and tests; shared route wiring remains in the Auth parent.
  - **Shared infrastructure stays at the parent**: `app/Auth/Models/` (domain models), `app/Auth/Database/{Migrations,Factories,Seeders}/` (migrations and factories are registered automatically by `AuthServiceProvider::loadMigrationsFrom`), `app/Auth/Providers/`, `app/Auth/routes/` (one file per concern, e.g. `trustedDevice.php`), and `app/Auth/config/`.
  - **Submodule convention (`app/Auth/Modules/<Feature>/`)** — established in SOC-14. The Auth submodules include `Email/`, `Login/`, `Password/`, `Register/`, and `TrustedDevice/`. A submodule mirrors the parent's *feature-side* layout (`Controllers/`, `Requests/`, `Services/`, `Listeners/`, `Resources/`, `Concerns/`, `Enums/`, `Tests/`) as applicable, but **does not duplicate providers, models, routes, migrations, or factories** — those stay shared at the parent so the feature integrates with the domain's wiring without owning its own bootstrap.
  - `AuthRouteServiceProvider` loads `routes/` (one file per concern); `AuthEventServiceProvider` registers Fortify listeners owned by Auth/TrustedDevice; User registers its recovery-codes listener through `app/User/Providers/UserEventServiceProvider.php`.
  - **Trusted device audit log (SOC-20)** — `app/Auth/Database/Migrations/2026_07_13_221739_create_trusted_devices_table.php` is the canonical combined migration for `trusted_devices` and the append-only `trusted_device_events` table. Events record discrete actions (`Created`, `Renewed`, `Renamed`, `Revoked`, `RevokedAll`) with a nullable `user_id` foreign key using `nullOnDelete`; device metadata is stored as a snapshot, so events do not depend on a `trusted_device_id` relation. Records are inserted via `TrustedDeviceEvent::record()` (static helper) from `TrustedDeviceService` and the `TwoFactorAuthenticationDisabled` listener; password changes and resets record bulk revocations through `PasswordTrustedDeviceRevoker`, which delegates to `TrustedDeviceService::revokeAll()`.
  - **Trusted device reactivation + GDPR purge (SOC-21)** — `TrustedDevice` uses Laravel's `SoftDeletes` trait (column `deleted_at`) so revoked devices stay in the table for re-confirmation. The `reactivate` endpoint always requires a 2FA code (verified inside `TrustedDeviceService::reactivate` since SOC-45; `TrustedDeviceReactivateRequest` only checks the format) before restoring the soft-deleted row and regenerating the token. The cookie fast-path described in the project's initial SOC-21 spec was deferred to a follow-up. The `force-destroy` endpoint (`DELETE /user/trusted-devices/{device}/force`, requires password confirmation via `TrustedDeviceDestroyForceRequest`) records a final `Revoked` event for snapshot continuity then `forceDelete()`s the row. The `TrustedDevicePurge` Artisan command (`trusted-devices:purge`) is registered in `AuthServiceProvider` (only when `runningInConsole()`) and scheduled daily at 03:00 — it `forceDelete()`s soft-deleted rows older than `module.auth.trusted_devices.purge_after_days` (default 90).
  - **Trusted device activity log dialog (SOC-22)** — `TrustedDeviceController::activity()` returns a standard `LengthAwarePaginator` (`paginate()`, not cursor pagination) over `trusted_device_events`, sanitized against whitelists via the shared `parseMultiFilter()` helper (also used for `status`/`browser`/`lastAccess` in `extractFilters()`): `action` and `since_days` are both comma-separated multi-select filters (`since_days` values `7|30|90|180|365`, applied as an OR'd multi-cutoff — `orWhere('created_at', '>=', now->subDays($days))` per selected value, same pattern as `lastAccess`); `null` on either means no filter, not a silent default. `search` is a case-insensitive `LIKE` against the denormalized snapshot columns `device_label`, `ip`, `device_os_name` (no join needed). `index()` exposes `activity()`'s result as a single `activityDialog` prop wrapped in `Inertia::optional()` — never sent on a standard visit, only resolved when the dialog fires a partial reload requesting it — so the two payload halves (`activityLog`/`activityFilters`) stay one prop instead of two independently-resolved `Inertia::optional()` closures that would otherwise call `activity()` twice per request.
  - **Trusted device controller → service split (SOC-37)** — `TrustedDeviceController` only handles HTTP: authorization, the `401` user narrowing, the `404` for non-revoked devices, cookie queueing and the flash. All state changes live in `TrustedDeviceService` (`register`, `rename`, `renew`, `revoke`, `forceDelete`, `reactivate`, `revokeAll`); each runs in a `DB::transaction`, records its `TrustedDeviceEvent`, and invalidates `TrustedDeviceDashboardCache` through `DB::afterCommit` (single private `recordEvent()` / `invalidateDashboardAfterCommit()` entry points). The service is the only reader of `module.auth.trusted_devices.cookie_lifetime_minutes` for renew/reactivate/create. `reactivate(User, TrustedDevice, string $otpCode, Request)` returns the raw token so the controller queues the cookie; `register()` returns a `TrustedDeviceOperationResult` and, when another request registers the same fingerprint between the pre-check and the `lockForUpdate` re-check, returns `AlreadyActive` (error flash, no cookie).
  - **Trusted device result enum + authorization (SOC-37)** — `TrustedDeviceOperationResult` is the single enum for the controller's flash outcomes (`Created`, `AlreadyActive`, `AlreadyRevoked`, `Renamed`, `Renewed`, `Revoked`, `RevokedAll`, `Reactivated`, `ForceDeleted`, `TwoFactorRequired`) and exposes `isSuccessful()`, `message()` and `payload()` (the array handed to `Inertia::flash()`); `register()` and `renew()` are the methods that return it. Ownership is enforced by `TrustedDevicePolicy` (`app/Auth/Modules/TrustedDevice/Policies/`), registered with `#[UsePolicy]` on the model (Laravel's naming-based discovery would not find it under `Modules/`) and applied in the controller with the `#[Authorize('<ability>', 'trustedDevice')]` method attribute (`update` for update/renew, `delete`, `restore` for reactivate, `forceDelete`). The attribute runs as middleware after route-model binding, so authorization precedes FormRequest validation.
  - **Trusted device enrollment hardening (SOC-45)** — "Active 2FA" means `User::hasEnabledTwoFactorAuthentication()` with Fortify's `confirm` option on (`two_factor_secret` and `two_factor_confirmed_at` both set); a pending secret never counts. `TwoFactorCodeVerifier` (`app/Auth/Modules/TrustedDevice/Services/`) is the single verifier: `hasConfirmedTwoFactor()`, `verifyTotp()`, `consumeRecoveryCode()` and `verifyCode()` (six digits are a TOTP, anything else is a single-use recovery code). The recovery-code part must run inside the caller's `DB::transaction`: it re-reads the user with `lockForUpdate` and consumes the code through `User::replaceRecoveryCode`, which removes it, so a code is single-use even under concurrent requests. Nothing it logs or returns contains codes or secrets. The login only skips the OTP with a valid, non-revoked, non-expired cookie of an account with confirmed 2FA (`TrustedDevice::validateAndTouch` checks it too); the cookie is the only credential and IP/User-Agent stay metadata. `TrustedDeviceInvalidate` is registered for both `TwoFactorAuthenticationDisabled` and `TwoFactorAuthenticationConfirmed` and revokes every device, so a cookie issued before confirmation can never bypass the OTP. There is deliberately no data migration for historical rows (nothing was in production when SOC-45 landed): revisit that before deploying with real data. `store` and `renew` require a current TOTP in `otp_code`: `TrustedDeviceStoreRequest` and `TrustedDeviceRenewRequest` share the `RequiresTwoFactorOtp` concern (error `two_factor` when 2FA is not confirmed, error `otp_code` when the code is missing or wrong; recovery codes are deliberately not accepted here: you already have a session and your authenticator at hand, whoever lacks it can sign in with a recovery code and tick remember-this-device, and every use would burn one of the 8 codes that are the backup against losing the phone), and `TrustedDeviceService::register()` / `renew()` repeat the check inside the transaction with the user row locked (returning `TwoFactorRequired`) so disabling 2FA concurrently cannot leave an active device behind. `reactivate()` verifies the code inside its transaction through `verifyCode()` (a TOTP or a recovery code consumed there), throws `ValidationException` (`two_factor` / `otp_code`) and rolls the consumption back if a later step fails. Disabling 2FA also accepts a TOTP or a recovery code: `TwoFactorDisableRequest` (User module) checks the format and verifies with the same `verifyCode()`; the recovery codes are wiped by the disabling anyway. Remembering the browser at login no longer adds a second row: `TrustedDeviceRemember` only calls `TrustedDeviceService::rememberAfterTwoFactorChallenge()`, which in one transaction reuses the latest row of the same fingerprint (user, user agent, system and IP) in any state through `TrustedDevice::findLatestForFingerprint()` — restoring it with a new token and an event `Reactivated` if it was revoked, `Renewed` if it was active or expired — and creates one with `Created` only for a browser never seen; before, revoking a device and signing in again with remember left the revoked row and a new active one (two devices for one browser). The four routes that check a two-factor code (`store`, `renew`, `reactivate` and the 2FA disable `destroy`) share one `throttle:two-factor-code` budget, defined in `FortifyServiceProvider` (5 per minute per user, per IP as a fallback), so alternating between them does not multiply the guesses a hijacked session can try (tested in `TrustedDeviceCodeThrottleTest`). Fortify rejects a replayed TOTP, so tests that reuse a code call `allowOtpReuse()` (`tests/Pest.php`). A test that sends a wrong code for a user with a TOTP secret uses `invalidOtpFor($user)`, which never matches a code of Fortify's verification window; a fixed `'000000'` would be the valid code about once in a million runs. Frontend: `TrustedDeviceIndexController` and `TwoFactorController::index` send a `twoFactorStatus` prop (`App\User\Modules\TwoFactor\Enums\TwoFactorStatus`: `disabled`, `pending`, `confirmed`) that `TrustedDeviceAddDialog` reads from the page props to show either a notice linking to the TwoFactor page or the OTP field; `TwoFactorOtpField` (six digits) and `TwoFactorCodeField` (the six digits or a recovery-code input, with a link to switch; it clears the value and the errors when switching and its mode resets when the dialog closes) live in `modules/setting/shared/components/`: the add and renew dialogs use `TwoFactorOtpField` (TOTP only), while `TrustedDeviceReactivationDialog` and the disable-2FA dialog (`DisabledTwoFactorDialog`, field `code`) use `TwoFactorCodeField`. The copy states that remembering a browser is a temporary convenience, not an independent second factor.

  - **Account status (SOC-35)** — `users.status` (string cast to `App\User\Enums\AccountStatus`: `active` / `suspended`, default `active`, indexed) is the only source of truth; it never derives from `email_verified_at` or `last_login_at`, and it is not in `#[Fillable]` (mass assignment throws). Every change also writes a row of the append-only `account_status_changes` table (`App\User\Models\AccountStatusChange`, morph `account_status_change`, no `updated_at`): `user_id` (`cascadeOnDelete`), `status`, a mandatory `reason` (max `AccountStatusChange::REASON_MAX_LENGTH`, 1000) and `changed_by` (the administrator, `nullOnDelete`). `User::isSuspended()` and `User::accountStatusChanges()` (most recent first) read them. `app/User/Modules/AccountStatus/Services/AccountStatusService` is the only writer: `suspend()` / `reactivate()` (account, administrator, reason) trim the reason (`InvalidArgumentException` when blank or too long), lock the user row, throw `LogicException` if it already has the target status, write the row and the status in one transaction, revoke every trusted device on suspension through `TrustedDeviceService::revokeAll()` (reactivating does not restore them), and record `admin.account_suspended` / `admin.account_reactivated` with the row as subject and only `target_user_id` (the reason lives only in `account_status_changes`). It does not authorize: `UserPolicy::suspend` (`admin.users.suspend`, an active account that is not the administrator's own) and `UserPolicy::reactivate` (`admin.users.reactivate`, a suspended account) do, applied by the Filament actions. A suspended account cannot sign in by any path: `LoginRequest::validateCredentials()` answers `AccountStatus::SUSPENDED_LOGIN_MESSAGE` only after the password matched (a wrong password still gets `auth.failed`, and neither fires `Failed` nor counts against the throttle), which also blocks the trusted-device OTP skip; `App\Auth\Modules\Login\Requests\TwoFactorLoginRequest` extends Fortify's and is bound in its place in `FortifyServiceProvider::register()`, so an account suspended between the password and the 2FA challenge is sent back to the login before any code is checked or consumed; `User::canAccessPanel()` rejects it; and the global `App\Http\Middleware\EnsureAccountIsActive` (parameters: guard and login route) ends an open or remember-me session on the next request (403 JSON for requests that expect JSON). It is appended to the `web` group, added to the admin panel middleware as `EnsureAccountIsActive:admin,filament.admin.auth.login` right after `AuthenticateSession`, and moved ahead of authentication with `prependToPriorityList(AuthenticatesRequests::class, …)` in `bootstrap/app.php`, otherwise Filament's `Authenticate` would answer 403 through `canAccessPanel()` before the session is ended. `AccountSettingsResource` exposes `status` read-only to its owner. Tests live in `app/User/Modules/AccountStatus/Tests/` (suite `AccountStatus`) and next to the code they cover in Login, Admin and ActivityLog.

The image route is `POST user/image/{userImageType}` (`user.update.image`): the segment must match the controller parameter `UserImageType $userImageType` for Laravel to bind the enum, and `UserImageUpdateRequest` reads `route('userImageType')`. It used to be `{type}`, which never bound and answered 500. Its tests live in `app/User/Tests/` (suite `User`, registered in `phpunit.xml` and `tests/Pest.php`).

- **Post** (`app/Modules/Post/`) — posts with images via `spatie/laravel-medialibrary`. First module on the new architecture (SOC-38): `Controllers/`, `Database/{Factories,Seeders}/`, `Models/`, `Providers/`, `Requests/`, `Resources/`, `Tests/`, `routes/`; namespace `App\Modules\Post\…`.
- **Comment** (`app/Modules/Comment/`) — polymorphic, self-referential (comments on posts and on other comments); second module on the new architecture (SOC-40): `Controllers/`, `Database/{Migrations,Factories,Seeders}/`, `Enums/`, `Models/`, `Props/`, `Providers/`, `Requests/`, `Resources/`, `Tests/`, `routes/`; namespace `App\Modules\Comment\…`.
  - **Behaviour and security rules (SOC-40, updated in SOC-46)** — the module's routes are `comments.store` (`POST comments`, `auth`+`verified`, `throttle:6,1,comments.store`), `comments.update` and `comments.destroy` (SOC-52, below), all served by `CommentController`, the module's single resource-style controller with one method per action (`store`, `update`, `destroy`); single-action controllers elsewhere stay invokable, while a module with several actions on one resource groups them in one controller (`CommentController`, `LikeController`). `store()` reads the validated input with the request's typed accessors (`string()`, `integer()`) and answers with the success flash `{type, message}`. The `throttle` third argument is a prefix because Laravel signs unnamed throttles by user only, so without it routes would share one budget. `CommentStoreRequest` and `CommentUpdateRequest` share the `NormalizesCommentContent` concern (`app/Modules/Comment/Concerns/`), which strips control characters (keeping tabs and line breaks) and trims `content` in `prepareForValidation()` before validating. Threads have a single level with a mention (SOC-41): a comment on a post can receive replies, and replying to a reply is allowed but is flattened. The client sends the comment it replied to as `commentable_id` (no extra request field); the controller attaches the new comment to the parent of the thread and stores the author of the replied reply in the nullable `replied_to_user_id` column (FK to `users`, `nullOnDelete`, so the mention disappears if that user is deleted). Replying to a post or to a root comment stores no mention. The user is derived on the server, so a forged `replied_to_user_id` in the request is ignored and a comment outside the thread can never be mentioned. `CommentResource` exposes the mention as `repliedTo: {id, name}` (or `null`) only when `repliedToUser` is loaded, and `CommentThreadProps` preloads it with `repliedToUser:id,name`, so listings keep a constant number of queries. Listings preload replies with `withCount('comments')` and `Comment::repliesCount()` reuses that `comments_count`, so serializing a page costs a constant number of queries. Regression tests live in `app/Modules/Comment/Tests/Security/`.
  - **Comment persistence naming (SOC-46)** — the `comments` migration lives in `app/Modules/Comment/Database/Migrations/` and `CommentServiceProvider::boot()` registers it with `loadMigrationsFrom`, like `AuthServiceProvider` and `UserServiceProvider`. It kept its original file name on purpose: a database that already ran it keeps treating it as run, so `php artisan migrate` does not try to recreate the table. It uses `morphs('commentable')`, so the columns are `commentable_type`/`commentable_id` and the relation is `Comment::commentable()`: Laravel's `{adjective}able` convention, the same one `likes` follows with `likeable`. `model_type`/`model_id` is the convention of generic package tables (Spatie's `media` and permission tables), not of domain tables, so it was deliberately not adopted here. `create_posts_table` still lives in the global `database/migrations/` folder.
  - **Comment data flow (SOC-46)** — there is no route that lists comments and no collection class. `CommentThreadProps` (`app/Modules/Comment/Props/`, an Inertia `ProvidesInertiaProperties`) is injected into `HomeController::__invoke` and `ProfileController::index/show` and exposes two props, `comments` (root comments of a post) and `replies` (replies of a comment), each `Inertia::optional(fn () => $cursorPaginator)`: they are never sent on a normal visit and only resolve on a partial reload that asks for them (`only`) with the thread in the query string, `comments_post=<id>` or `replies_comment=<id>`. Pages are `cursorPaginate(10)` with their own cursor names (`comments_cursor`, `replies_cursor`, so they do not collide with the `cursor` of `posts`), ordered by descending id for the comments of a post (newest first) and by ascending id for the replies of a comment (oldest first, so a conversation reads in order and a new reply is the last one), serialized with `->through(CommentResource)` and loaded with `user` + `withCount('comments')`. A missing or non-positive-integer id answers 404 and an unknown thread raises `ModelNotFoundException` (also 404). They return the plain paginator, not `Inertia::scroll(...)`: the hook always reloads with `reset` and keeps its own state, so the merge instruction (`mergeProps`) and scroll metadata (`scrollProps`) that `Inertia::scroll` adds to every response would be unused payload. `props.comments` and `props.replies` are the paginator envelope (`data`, `path`, `per_page`, `next_cursor`, `next_page_url`, `prev_cursor`, `prev_page_url`), pinned by `CommentThreadPropsTest`. The read budget is 60 per minute per user, enforced inside `CommentThreadProps` with `RateLimiter` under its own key (`comments.index`, separate from `comments.store`) and answers 429 with `Retry-After`. The success flash of `comments.store` is the only use of flash in the module. Tests live in `app/Modules/Comment/Tests/Props/` (`CommentThreadPropsTest`, `CommentThreadHostPagesTest`) and in `Tests/Security/` (throttle and query-count tests drive the home page with an Inertia partial-reload request).
  - **Comment likes in the listing (SOC-51)** — `CommentResource` adds `likesInfo: {count, likedByMe}` (`Comment::likesCount()` and `Comment::isLikedBy(User)` reuse the preloaded `likes_count` and `liked_by_me`; for a guest `likedByMe` is false without a query). `CommentThreadProps` preloads them in the same paginated query with `withCount(['comments', 'likes'])` and `withExists(['likes as liked_by_me' => …whereBelongsTo($user)])`, so the number of queries stays constant (`CommentQueryCountTest` adds likes to the large thread).
  - **Edit and delete own comments (SOC-52)** — a new migration in `app/Modules/Comment/Database/Migrations/` adds `edited_at` and `softDeletes()` to `comments` (the original migrations are untouched). `CommentPolicy` (`app/Modules/Comment/Policies/`, registered with `#[UsePolicy]` on the model) allows `update` and `delete` only to the author and never on a deleted comment; `CommentController::update()` and `destroy()` apply it with `#[Authorize('update'|'delete', 'comment')]`, which runs after route-model binding and before the FormRequest, so a stranger gets 403 even with invalid input. `PATCH comments/{comment}` (`comments.update`, `throttle:10,1,comments.update`) accepts only `content` (`CommentUpdateRequest`, required, max `Comment::CONTENT_MAX_LENGTH` (1000), same normalization as creating) and sets `edited_at = now()` only when the content changed. `DELETE comments/{comment}` (`comments.destroy`, `throttle:10,1,comments.destroy`) deletes inside a `DB::transaction`: a comment with replies is deleted logically and becomes a **tombstone** (its likes are kept but never serialized); a comment without replies is deleted for good together with its likes (`likes` has no foreign key, so `$comment->likes()->delete()` is explicit); and when the deleted one was the last reply of an already deleted parent, the parent and its likes are deleted for good too, so no empty tombstone is left. A deleted comment is always a top-level one that had replies; replies are never tombstones. Because of `SoftDeletes`, route-model binding answers 404 for a deleted comment, `Post::comments()`, `User::comments()` and the Admin panel no longer see tombstones (moderation from Admin is out of scope), and `CommentThreadProps` lists root comments with `withTrashed()` and finds the parent of a reply list with `withTrashed()` so the replies of a tombstone still load. `CommentController::store()` answers 404 when commenting directly on a tombstone but accepts a reply to a reply of a thread whose root is a tombstone (the parent is looked up with `withTrashed()`). `CommentResource` adds `editedAt`, `isDeleted` and `isMine` (the comment's author is the authenticated user; no Gate, so no extra query) and serializes a tombstone as `{id, content: null, createdAt, editedAt: null, isDeleted: true, isMine: false, user: null, repliesInfo, likesInfo: zero}`; each block of the payload lives in a private method (`author()`, `repliedTo()`, `repliesInfo()`, `likesInfo()`, `isMine()`, `tombstone()`). `[H8]` in `CommentSecurityAuditTest` now pins the exact list of `comments.*` routes. Tests live in `Tests/{Crud,Policies,Requests,Resources,Props,Security,Seeders}/`; the query-count test includes edited and deleted comments.
- **Like** (`app/Modules/Like/`) — polymorphic likes (`likes` table, morph `like`, column `likeable`) on posts and comments; third module on the new architecture (SOC-51): `Controllers/`, `Database/{Factories,Migrations,Seeders}/`, `Models/`, `Providers/`, `Tests/`, `routes/`; namespace `App\Modules\Like\…`. Comments and posts can be liked from the UI.
  - **Persistence and migration (SOC-51)** — `LikeServiceProvider` (registered in `bootstrap/providers.php`) calls `loadMigrationsFrom` and registers `LikeRouteServiceProvider`. `create_likes_table` moved from the global `database/migrations/` into `app/Modules/Like/Database/Migrations/` keeping its original file name, so a database that already ran it does not run it again.   - **Toggle endpoint (SOC-51)** — `POST comments/{comment}/like` (`comments.like`, `toggleComment`) and `POST posts/{post}/like` (`posts.like`, `togglePost`), both `auth`+`verified` with `throttle:30,1,<route name>` (each its own budget, separate from `comments.store`), are served by `LikeController`, which shares a private `toggle()` between both actions (SOC-50), and answer JSON `{liked: bool, likesCount: int}`: it is the only JSON route and it is consumed with Inertia v3's `useHttp`, a standalone request that does not trigger a page visit and does not depend on the host page, so Home and Profile share it. Any authenticated user can like any comment, including replies and their own; there is no visibility rule because posts and comments have none (add a policy if private posts ever exist). The unique index settles a double click or two tabs: a `UniqueConstraintViolationException` while creating counts as "already liked". `verified` filters nobody today because `User` does not implement `MustVerifyEmail`, in every route of the project.

A rejected action records nothing.

## High-level architecture

### Modular service-provider pattern

Each domain registers itself through **two providers** wired up in `bootstrap/providers.php`. Paths below use `app/<Domain>/` for the old architecture; a migrated module lives at `app/Modules/<Domain>/` with the same layout (e.g. `App\Modules\Post\Providers\PostServiceProvider`):

1. `<Domain>ServiceProvider` (`app/<Domain>/Providers/`) — a thin provider whose `boot()` registers the domain's `<Domain>RouteServiceProvider`.
2. `<Domain>RouteServiceProvider` (`app/<Domain>/Providers/`) — extends `Illuminate\Foundation\Support\Providers\RouteServiceProvider`, loads routes from `app/<Domain>/routes/routes.php` under the `web` middleware group.

When adding a new domain: create it under `app/Modules/<Domain>/`, create both providers, register the outer one in `bootstrap/providers.php`, add a `routes/routes.php` (or for Auth, split per concern under `app/Auth/routes/`).

### Admin panel (Filament + Spatie Permission)

The dashboard replaces Filament's `FilamentInfoWidget` with `AdminQuickLinksWidget` (permission-filtered navigation; its Announcements link asks `AnnouncementPolicy::viewAny` through `Gate`, SOC-61) and `OperationalSummaryWidget` (permission-gated account, activity, and backup metrics). Admin data transfer objects live in `app/Modules/Admin/Data/`; `DashboardBackupSummaryData` stores backup aggregates without archive filenames, while `BackupSummaryWidget` receives listing data from `BackupManagement::getWidgetData()`.

`Admin` is a system module and exception to the standard two-provider/module-route pattern. `app/Modules/Admin/Providers/AdminPanelProvider.php` is registered in `bootstrap/providers.php`; it configures panel id `admin`, path `/admin`, guard `admin`, and discovery under `app/Modules/Admin/Filament/`. The `admin` session guard uses the existing `users` provider; `web` remains the application's default guard. Filament supplies the panel routes, so don't add duplicate routes in a module `routes/` directory.

Keep Filament resources in the generated per-resource hierarchy under `app/Modules/Admin/Filament/Resources/<PluralModel>/`: the resource class at the directory root, and its `Pages/`, `Schemas/`, and `Tables/` in their own subdirectories as needed. The current User resource is `Users/UserResource.php`, with list/detail pages in `Users/Pages/` and the table definition in `Users/Tables/UsersTable.php`. Follow the [Filament 5 resource documentation](https://filamentphp.com/docs/5.x/resources/overview) when extending this layout. **Announcements (SOC-61)** — `Announcements/AnnouncementResource.php` (model `App\Modules\Announcement\Models\Announcement`, URL `/admin/announcements`, navigation label 'Announcements') has no `can*()` overrides: Filament asks `AnnouncementPolicy`. **Panel languages (SOC-65 and SOC-66)** — the admin panel speaks Spanish and English. `User::canAccessPanel()` requires the `admin` panel, a verified email, an account that is not suspended (SOC-35), and `admin.access`; `AdminPanelProvider` also requires app-based MFA. Section access is checked through permissions, so `admin.access` alone does not grant access to dashboard, Users, Posts, the activity log, Announcements, or Backups. The catalog defaults are assigned when each role is first created; use the authorization commands below for later operational changes. **Authorization lives in the model policy (SOC-57)**: resources do not override `can*()`; Filament asks the policy of the resource's model, and relation managers and widgets ask the same policy through `Gate::forUser($user)->allows('viewAny', Model::class)` / `allows('view', $record or Model::class)` instead of checking `AdminPermission` directly (only the invite action of `ListUsers` and the dashboard and Backups pieces, which have no model, still check permissions). Filament allows any ability whose method the policy does not define, so a read-only policy must deny every write ability explicitly. `UserPolicy` controls read access to User records, allows only `suspend` and `reactivate` among the writes (SOC-35, see the User section) and denies every other mutation; `ActivityLogPolicy` does the same for the activity log; `AnnouncementPolicy` (`app/Modules/Announcement/Policies/`, SOC-61) allows each panel ability with its own permission, `replicate` with `admin.announcements.create`, denies `deleteAny`, `restore`, `restoreAny`, `forceDelete` and `forceDeleteAny`, and adds the application's `dismiss`; `PostPolicy` (`app/Modules/Post/Policies/`) for posts (`viewAny` with `admin.posts.viewAny`, `view(User, ?Post)` with `admin.posts.view` and, given a post, only while it still has its author; without a post it serves the static `canView()` of widgets, and it denies `create`, `update`, `delete`, `deleteAny`, `restore`, `restoreAny`, `forceDelete` and `forceDeleteAny`). `CommentPolicy` adds the panel's `viewAny` and `view` (both `admin.posts.view`; comments have no permissions of their own) next to the application's `update`/`delete`, which let the author change their own comment, so `CommentResource` keeps every write ability (`canCreate`, `canEdit`, `canDelete`, `canDeleteAny`, `canRestore(Any)`, `canForceDelete(Any)`) pinned to `false` with a docblock explaining why: these are the only authorization overrides left in Admin resources. User's table/detail view exposes only name, email, account status (badge, plus a status filter in the table), verification/creation timestamps, and last login; keep credentials and 2FA secrets out of Filament output. `ViewUser` has the header actions 'Suspend account' and 'Reactivate account' (confirmation modal with a required 'Reason', authorized with `->authorize('suspend'|'reactivate')`, calling `AccountStatusService`; when another tab changed the status while the modal was open, `ViewUser::callMountedAction()` sends the action's failure notification ('already suspended' / 'already active') and closes the modal without writing, because Filament's own re-check of the policy would otherwise drop the call silently), and the read-only 'Status history' tab (`Users/RelationManagers/AccountStatusChangesRelationManager`: date, status, reason and 'Changed by', or 'Deleted user'). Badge label, color and filter options come from `Filament/Concerns/DescribesAccountStatus.php`.

`DatabaseSeeder` runs `AdminAuthorizationSeeder` and `AdminUserSeeder`. The authorization seeder creates the catalog under Spatie's `admin` guard. In `local` and `testing`, `AdminUserSeeder` assigns Angel (`angel@gmail.com`) the base role and all five reader roles (`AdminUserSeeder::readerRoles()`: dashboard, users, posts, activity and backups; the provisioner role is never assigned automatically; Angel also gets `admin-users-moderator`, since SOC-35, `admin-backups-operator` and `admin-announcements-manager`, since SOC-61, so those flows can be tried locally; random administrators never get them), then promotes random users until at least 20% of all users (rounded up, counting Angel and anyone already holding `admin`) are administrators; each one gets `admin` plus a random, non-empty subset (1 to 4) of the five reader roles. It preserves existing role assignments and is idempotent. The seeded administrators have roles but cannot enter the panel without app-based MFA, which seeders do not configure. For production bootstrap, initialize the catalog and promote an existing verified account:

```bash
php artisan db:seed --class='App\Modules\Admin\Database\Seeders\AdminAuthorizationSeeder'
php artisan admin:bootstrap-admin admin@example.com --actor=admin@example.com
```

Every Admin command requires `--actor=<email>`, the person running it, who is recorded as the causer in the `admin` activity log (SOC-54). The actor must exist and be verified; for `admin:user-role` and `admin:role-permissions` it must also hold `admin.access`, while `admin:bootstrap-admin` accepts any verified actor, including the promoted user, because no administrator exists yet. A missing `--actor` answers `INVALID` and a rejected actor `FAILURE`, both without changes. Only real changes are recorded (`admin.bootstrapped` with the assigned `roles`, `admin.role_granted` / `admin.role_revoked` with the target user and `role`, `admin.role_permission_granted` / `admin.role_permission_revoked` with the `Role` as subject); a repeated grant or a revocation blocked to protect the last `admin.access` records nothing. The validation lives in `InteractsWithAdminCatalog::actorEmail()` and `resolveActor()`, which the three commands share.

`admin:bootstrap-admin <email> --actor=<email>` runs once: it requires the authorization catalog, rejects unverified accounts, refuses a second bootstrap after `admin.access` exists, and assigns `admin` plus all five reader roles (activity and backups included since SOC-56 and SOC-55). Later, `admin:user-role <grant|revoke> <email> <role> --actor=<email>` assigns or revokes one catalog role for an existing user; valid roles are every `AdminRole` case: `admin`, `admin-dashboard-reader`, `admin-users-reader`, `admin-users-provisioner`, `admin-users-moderator`, `admin-posts-reader`, `admin-activity-reader`, `admin-backups-reader`, `admin-backups-operator`, and `admin-announcements-manager`. `admin:role-permissions <grant|revoke> <role> <permission> --actor=<email>` changes a role's catalog permissions; valid permissions are every `AdminPermission` case: `admin.access`, `admin.dashboard.view`, `admin.users.viewAny`, `admin.users.view`, `admin.users.create`, `admin.users.suspend`, `admin.users.reactivate`, `admin.posts.viewAny`, `admin.posts.view`, `admin.activity.viewAny`, `admin.activity.view`, `admin.backups.view`, `admin.backups.create`, `admin.backups.download`, `admin.announcements.viewAny`, `admin.announcements.view`, `admin.announcements.create`, `admin.announcements.update`, and `admin.announcements.delete`. Both commands reject identifiers outside their enums and protect the last `admin.access` grant. Role and permission management remains command-line based; SOC-44 does not add a management screen.

### Strict typing & static analysis

- Rector is configured for PHP 8.5; new typed class constants use `private const string NAME = '...';` syntax (see `FortifyServiceProvider` for the pattern).
- Los agentes de IA deben ejecutar `composer rector-dry` y `composer rector` en toda tarea que modifique PHP, aunque no sea un refactor grande. Rector es un gate obligatorio y no requiere aprobación adicional. Orden del gate: `composer rector-clear-cache` → `composer rector-dry` → `composer rector`. Ejecútalo siempre sobre todo el proyecto (sin pasar rutas): reglas como `RenameVariableToMatchMethodCallReturnTypeRector` necesitan los tipos de otros archivos (p. ej. los helpers de `tests/Pest.php`) y con una ruta parcial o con la caché de Rector pueden no detectar lo que el CI (`backend-rector`) sí marca.

### Naming — no single-letter variables

- Variables, parameters, and closure-captured values must be a **full descriptive word** (e.g. `$candidate`, `$device`, `$browserFilter`). Single-letter names like `$v`, `$i`, `$e`, `$x` are forbidden because they force the reader to decode intent from context.
- The only acceptable exception is a numeric `for` loop counter (`for ($i = 0; $i < count($arr); $i++)` is idiomatic PHP). Even there, prefer `foreach` over indexed `for` whenever possible.
- TypeScript follows the same rule (see `AGENTS.md`).

### Media uploads

Files are handled via `spatie/laravel-medialibrary` with a custom path generator (`app/Support/MediaLibrary/MediaLibraryCustomPathGenerator.php`, wired in `config/media-library.php`; Post media lives in `posts/{media id}/` and the rest, announcement images included, in `{media id}/`, so changing it would orphan stored files). The `app:clean-media-library-folders` command deletes everything under `storage/app/public` and `public/storage`, so it is prohibited in production (`MediaLibraryCleanFoldersCommand::prohibit()` in `AppServiceProvider::boot()`). Controllers catch `FileDoesNotExist|FileIsTooBig` and surface a flash notification via `back()->with('notification', [...])` or `Inertia::flash([...])->back()`. The notification shape is `{type: 'success'|'error', message: string, action?: {label, url}}`.

**Storage disks (SOC-62)** — MediaLibrary writes to `MEDIA_DISK` (default `public`). `config/filesystems.php` defines a dedicated `media` disk (driver `s3`, `visibility` public) with its own bucket and public URL (`MEDIA_S3_BUCKET`, `MEDIA_S3_URL`); its credentials and connection use `MEDIA_S3_ACCESS_KEY_ID`, `MEDIA_S3_SECRET_ACCESS_KEY`, `MEDIA_S3_DEFAULT_REGION`, `MEDIA_S3_ENDPOINT` and `MEDIA_S3_USE_PATH_STYLE_ENDPOINT` with `AWS_*` as fallback, the same pattern as `backups`, so images can live on another provider or account without touching the backups. `MEDIA_DISK=media` turns it on; the media disk never reads `AWS_BUCKET` or `AWS_URL`, which belong to the general `s3` disk that nothing uses today (nor does any code use `FILESYSTEM_DISK`). `.env.example` keeps the `AWS` block above the media and backup blocks because their credentials are `"${AWS_...}"` and phpdotenv only resolves variables already defined; variables coming from the platform instead of a `.env` file are not interpolated, and then the `config/` fallback applies. A local S3 emulator (LocalStack, MiniStack) needs `AWS_ENDPOINT=http://localhost:4566` and `AWS_USE_PATH_STYLE_ENDPOINT=true`. `.env.testing` defines no `MEDIA_DISK`, so tests stay on `public`. `tests/Pest.php` has `configWithEnvironment()` and `filesystemDiskWithEnvironment()` to evaluate `config/filesystems.php` with temporary environment variables (config() is already loaded in a test); they copy and restore the whole `$_SERVER`/`$_ENV` because rector-laravel rewrites single superglobal reads (even inside `unset()`) into invalid code. Tests: `tests/Feature/MediaLibrary/MediaDiskConfigurationTest.php` and `app/Modules/Admin/Tests/Backups/BackupConfigurationTest.php`.

### Seeders (random, two-factor-aware data)

`DatabaseSeeder` runs `UserSeeder` → `AdminAuthorizationSeeder` → `AdminUserSeeder` → `TrustedDeviceSeeder` → `AccountStatusSeeder` → `AnnouncementSeeder` → `PostSeeder` → `CommentSeeder` → `LikeSeeder` → `ActivityLogSeeder`. Counts are random and skewed (many low values, few high ones) through `App\Support\Seeding\SkewedRandom::count($min, $max, $skew)` (`mt_rand` based, `$skew` 1 is uniform): posts per user 0–50 (skew 3; 60% of the posts get a seeding image through `PostFactory::withImage(60)`), root comments per post 0–10 and replies per root comment 0–6 (skew 2), likes per comment 0–8 (skew 3, distinct users), devices per confirmed-2FA user 0–30 (skew 2). Choices with probabilities go through `App\Support\Seeding\WeightedRandom` (`pick($weights)` returns a key in proportion to its weight, `chance($percent)` is a yes/no draw). Every comment, root or reply, draws its own random author (`CommentSeeder::createComments()`; before, all root comments of a post shared one author); replies keep the single-level thread and the mention of another reply author. About 10% of the comments are marked edited (`edited_at` after `created_at`) and about 10% of the root comments that have replies are deleted, which leaves tombstones (SOC-52). `UserSeeder` creates 200 users (constructor argument `$userCount`) with exact shares in random order: 25% with `UserFactory::twoFactorConfirmed()`, 5% with `twoFactorPending()` (a real TOTP secret and eight Fortify-format recovery codes) and the rest without 2FA; half of them, drawn with `WeightedRandom::chance()`, get a random seeding profile picture and cover image through `UserFactory::withImages()`. Angel (`UserSeeder::TEST_USER_EMAIL`) is created last, never with 2FA, so the local login does not ask for an OTP; seeded 2FA secrets are random, so those users are for browsing screens, not for signing in. Angel is created with `forceCreate` because `email_verified_at` is not mass assignable. `TrustedDeviceSeeder` follows the SOC-45 rules and has no fixed scenarios: every confirmed-2FA user gets a random number of devices and each device picks its state with weights (active 45%, expiring soon 10%, expired 25%, revoked 20%) through the `TrustedDeviceFactory` states `active()`, `expiringSoon()`, `expired()` and `revoked()`, plus the events that explain it, each dated after the previous one and with the device's own dates (`Created` when the device was created; an active device may also have `Renamed` 20%, `Renewed` 15% — its trust then runs 30 days from the renewal — or `Revoked` followed by `Reactivated` 10%, which leaves it active; a revoked device has `Revoked` at its `deleted_at`). A share of the users without 2FA (5%, constructor argument `$formerTwoFactorSharePercent`, never Angel) are the ones who disabled it and only have revoked devices with `RevokedAll` events; pending users and everyone else have none. `TrustedDeviceFactory` generates coherent devices (a `public const TRUST_LIFETIME_DAYS` of 30): about 40% mobile (15% of those tablets), iOS or Android for mobile and Windows, Mac or Linux for desktop, a browser that exists on that system (Safari only on Mac and iOS, Edge only on Windows), an OS version, a name and a user agent built from the same system and browser, so `DeviceDetector` reads the user agent as the stored system, browser, version and device type (checked in `TrustedDeviceFactoryTest`). Its default state keeps the old dates (expires in 30 days) so the many tests that use it do not change; the date-coherent states are for seeding. Seeder tests cannot rely on `mt_srand` (`UserFactory::withImages()` and `PostFactory::withImage()` pick an image with `array_rand`, which consumes the same `mt_rand` sequence, only when the unversioned seeding images exist, so the sequence differs between a local checkout and CI), so they assert ranges and properties over enough samples and never that a specific value occurs; that a count can be 0 is covered by `tests/Unit/Support/Seeding/SkewedRandomTest.php`. `ActivityLogSeeder` (`app/Modules/ActivityLog/Database/Seeders/`, SOC-56) runs last and derives the activity from what the other seeders created, so every record points to something real: `content.post_created` per post; `content.comment_created` (with `post_id`) or `content.comment_replied` (with `thread_comment_id`) per comment, plus `content.comment_updated` for edited ones and `content.comment_deleted` (`permanently` false) for tombstones; `likes.added` per like; a `trusted_devices.*` mirror per `TrustedDeviceEvent` with its own date, IP and user agent; per user, 0–20 logins (skew 2, most with their logout), a few anonymous failed logins on their account, occasional password changes and `auth.two_factor_confirmed` for confirmed 2FA; `admin.account_suspended` / `admin.account_reactivated` per `AccountStatusChange` with its real date and only `target_user_id`; the `admin.announcement_*` audit derived from the seeded announcements (see the Announcement entry); and Angel's `admin.bootstrapped` followed by an `admin.role_granted` (Angel as actor, no IP) for every role of the other administrators. Because the content seeders create everything at seeding time, its dates are spread over the last 60 days (edits and deletions after their creation, never in the future) instead of copying the records' `created_at`, so the activity list and its date filter have variety; device mirrors keep their real dates. Web actions get a fake IP and user agent, properties use only allowed keys and never content, rows are inserted 1000 at a time through the `ActivityLog` model, and the seeder does nothing when `activity_log` already has rows, so running it twice does not duplicate. A full `migrate:fresh --seed` produces about 65 000 rows in three seconds. Tests live in `app/Modules/ActivityLog/Tests/Seeders/ActivityLogSeederTest.php`. `AccountStatusSeeder` (`app/User/Database/Seeders/`, SOC-35) picks, among accounts that are neither administrators nor Angel, about 3% to suspend (a row with a sample Spanish reason and a random seeded administrator, dated after the account's last device activity, with its active devices soft deleted at that date plus a `RevokedAll` event created through the factory) and about 3% of the accounts without trusted devices for a past suspension followed by a reactivation (constructor arguments `$suspendedSharePercent` and `$reactivatedSharePercent`). It never uses `AccountStatusService` or `TrustedDeviceEvent::record()`, so it writes no `activity_log` rows and `ActivityLogSeeder` still runs; it does nothing when `account_status_changes` has rows or nobody holds `admin`. Tests live in `app/User/Modules/AccountStatus/Tests/Seeders/AccountStatusSeederTest.php`.

- Use all Inertia features from v1, v2, and v3. Check the documentation before making changes to ensure the correct approach.
- New v3 features: standalone HTTP requests (`useHttp` hook), optimistic updates with automatic rollback, layout props (`useLayoutProps` hook), instant visits, simplified SSR via `@inertiajs/vite` plugin, custom exception handling for error pages.

- SSR works automatically in Vite dev mode with `@inertiajs/vite` - no separate Node.js server needed during development.
- Event renames: `invalid` is now `httpException`, `exception` is now `networkError`.
- `router.cancel()` replaced by `router.cancelAll()`.
- The `future` configuration namespace has been removed - all v2 future options are now always enabled.
