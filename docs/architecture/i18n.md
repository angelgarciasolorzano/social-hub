# Languages (admin panel and application)

How the Filament panel (SOC-65, SOC-66) and the React application (SOC-67) speak Spanish and English. `lang/` at the project root is the only source of translations. The coding rules live in `.ai/rules/backend.md` and `.ai/rules/frontend.md`.

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

## Admin panel (SOC-65 and SOC-66)

**Panel languages (SOC-65 and SOC-66)** — the admin panel speaks Spanish and English. Translations live in `lang/{en,es}/` at the project root (Laravel's convention; `resources/lang/` was moved there and no longer exists). The panel's texts are in one catalog per section, `lang/{en,es}/admin/{common,dashboard,users,backups,activity-log,announcements,posts,comments,roles}.php`, with named keys (`admin/users.table.status`, never the English text as the key), plurals through `trans_choice` and placeholders as parameters (`:name`, `:count`; Laravel's `:Type` capitalizes the value). In PHP every text goes through `App\Support\Translation\TranslatedText::of($key, $replace)`, which is `__()` typed as `string` (it throws `LogicException` when the key names a group) so PHPStan accepts it where Filament expects a string; Blade views use `__()`. Text properties (`$title`, `$heading`, `$navigationLabel`, `$navigationGroup`, a relation manager's `$title`, a chart's `$emptyStateHeading`…) cannot call a function, so those classes override the matching getter (`getTitle()`, `getHeading()`, `getNavigationLabel()`, `getNavigationGroup()`, `getModelLabel()`, `getPluralModelLabel()`, the static `RelationManager::getTitle()`…). A badge's color or icon never compares its translated label: it depends on the record or on a key (`TrustedDevicesRelationManager` keeps `active`/`expired`/`revoked` as the state and only translates its label). Dates use `translatedFormat()` with a format from the catalog. Filament's own texts (login, MFA, profile, buttons, pagination, filters) come translated with Filament. The language switch is the approved plugin `bezhansalleh/filament-language-switch` (5.x), configured in `AdminServiceProvider::configureLanguageSwitch()`: locales `en` and `es` (`AdminServiceProvider::SWITCH_LOCALES`, cases of `App\User\Enums\PreferredLocale`; English goes first because, for a browser that asks for no offered language, the plugin picks the first locale, which must match `app.locale`), shown inside the panel and on the sign-in, required MFA set-up and profile pages (route names built from the panel; not on the invitation acceptance page). The plugin resolves the locale from the session, `?locale=`, the administrator's `users.preferred_locale` (read with `Filament::auth()`, never `auth()`, which is the `web` guard inside the panel), the browser's `Accept-Language`, its cookie and `app.locale`; an unsupported value falls back to `app.locale`. Choosing a language fires `LocaleChanged`, and `App\Modules\Admin\Listeners\StoreAdminPreferredLocale` saves it as `preferred_locale` (only an offered locale, without auditing it); that column is the same one the application's account settings edit. The plugin adds its `SwitchLanguageLocale` middleware to the panel routes only, so `AdminServiceProvider` also registers it with `Livewire::addPersistentMiddleware()`: without it every Livewire update (filtering, sorting, paginating, opening a modal) would answer in `app.locale`. Translated today: Dashboard (its four widgets), Users (resource, table, invitation, detail, suspend/reactivate, the four relation managers and its widget, plus `AccountStatus::label()`), Backups (page, table, destination and retention details, summary widget and `BackupManagementService` download errors), Activity Log (resource/table, detail, overview and summary widgets, party labels, event and log names; `ActivityLogEventCatalog` reads `admin/activity-log.events.<value>` and `logs.<log>`, falling back to its English name), Announcements (resource, form, table, tabs, actions, detail, preview, and enum labels/descriptions), and Posts (resource, table, detail, both overview widgets, and the Comments relation manager nested in `PostResource`). Roles (SOC-69: resource, table, detail, actions, relation managers, widgets, permission matrix, catalog names and the role pieces of Users) is translated as it was built. SOC-66 also translates the standalone Comments resource: it has no index or navigation entry, exposes a read-only detail route, and localizes the detail, replies table/modal, and activity metrics under `CommentPolicy` with `admin.posts.view`. Announcement, post, and comment content authored by administrators or users keeps the language its author entered. The admin invitation email and acceptance page with `AdminInvitationService` messages, and the names of Spatie's failed backup checks, remain outside the translated panel scope. Two tests guard the result: `app/Modules/Admin/Tests/Translations/AdminTranslationKeysTest.php` requires matching keys, non-empty texts, and matching placeholders in `en` and `es` for every admin catalog, plus the presentation keys for announcement enums, a name for each cataloged activity event, log, and morph type, and a name and description for each cataloged role and permission and a name for each permission area (SOC-69); `app/Modules/Admin/Tests/Translations/AdminHardcodedTextTest.php` scans Activity Log, Announcements, Posts, standalone Comments, Roles (SOC-69, with the permission matrix view and `ConfirmsCurrentPassword`), and the announcement preview for literals passed to Filament text methods, `Tab::make()`, `Stat::make()`, `Section::make()`, text properties, or plain Blade text. It excludes model-backed authored content while scanning the translated Comments resource. Every new panel text is written this way (rule in `.ai/rules/backend.md`).

## Application (SOC-67)

The React application speaks Spanish and English, starting with the settings pages: **Profile** (`setting/modules/accountSettings`), **Two-factor authentication** and **Trusted devices**. `lang/` at the project root is the **only source of translations** for PHP and React: there is no second catalog under `resources/js` and no i18n package. `laravel-react-i18n` was rejected because it lists `react ^18` as a dependency (a second React copy next to React 19) and has not been released since 2024, and `@erag/lang-sync-inertia` because it requires Vue, Svelte, `@inertiajs/vue3` and `@inertiajs/svelte` as peers (27 packages in a dry run), applies no fallback per key, and its PHP package replaces Laravel's global `Lang` alias and adds a global middleware. The design follows erag's idea (catalogs per page in props) with our own code.

- **Language of a request** — `App\Http\Middleware\SetApplicationLocale`, appended to the `web` group right before `HandleInertiaRequests`, applies the signed-in user's `preferred_locale` (read with `getRawOriginal()` + `PreferredLocale::tryFrom()`, so an unsupported stored value does not throw and is treated as a guest), else the first supported language of `Accept-Language` in the browser's order (checked explicitly: `getPreferredLanguage()` returns the first offered locale even when none matches), else `SetApplicationLocale::GUEST_FALLBACK_LOCALE` (Spanish). `app.locale` and `app.fallback_locale` stay `en` (the panel's language switch needs `app.locale` in English); the panel keeps applying its own language through `SwitchLanguageLocale`. `RegisterUserController::store()` saves the resolved language as the new account's `preferred_locale` (the column's default is `en`, so existing accounts see English until they change it in Profile; there is no data migration). `AccountSettingsController::update()` applies the language just saved before building its flash, so the next page arrives in one language. `UserSeeder` creates Angel with `es`.
- **Catalogs for React** — `App\Support\Translation\FrontendTranslations` (request-scoped through `#[Scoped]`) collects the groups a page needs: a controller calls `use('setting/common', …)` before `Inertia::render()` (`AccountSettingsController::edit`, `TwoFactorController::index` — which also registers both trusted device groups because the page shows that panel and its dialogs —, `TrustedDeviceIndexController` and `PreferenceController::appearance`, which only registers `setting/common` for the sidebar). `toArray()` returns each group in the active locale merged key by key over the fallback locale (`array_replace_recursive`), so a key missing in `es` reaches React in English; an unknown group throws `InvalidArgumentException`. `HandleInertiaRequests::share()` adds `locale` and `translations` (a closure, so a partial reload that asks for another prop does not resend it and React keeps the previous value) and always registers `dates`. `SharedData` types them as `locale: Locale` (`"en" | "es"`, a mirror of `PreferredLocale`) and `translations: Record<string, TranslationTree>`.
- **Catalogs** — `lang/{en,es}/setting/{common,account-settings,two-factor,trusted-devices,trusted-device-dialogs}.php` (one per page, plus `common` for the sidebar, the buttons every dialog repeats and the two-factor code fields; the dialogs of the trusted devices page have their own file), `lang/{en,es}/dates.php` (dayjs formats and the "never"/"not available"/"expired" texts) and `lang/{en,es}/validation.php` (Laravel's default messages copied from the framework, translated to Spanish, with `attributes` for the settings fields). Keys are named (`setting/trusted-devices.table.open_actions`), plurals use Laravel's syntax (`{1} …|[0,*] …`) and values are placeholders (`:name`, `:count`). A text with an emphasized part is split into `_before`/`_after` (or `_emphasis`) keys so the markup stays in the component.
- **React** — `useTranslation()` (`shared/hooks/useTranslation.ts`) returns `{ t, tChoice, locale }` bound to the page's `translations`; `t`/`tChoice` are `useCallback`s that keep their identity while the translations do not change, so they are safe as hook dependencies. The pure functions live in `shared/lib/translation.ts` (`translate`, `translateChoice`: lookup of `group.nested.key`, `:name`/`:Name`/`:NAME` like Laravel, longer placeholders first, and the `{n}`, `{a,b}`, `[from,to]` and `one|many` plural forms; a missing key returns the key). Nothing keeps the language in module state, so SSR never mixes languages between requests. `useDateTime()` (`shared/hooks/useDateTime.ts`) returns the date helpers of `shared/lib/dateTime.ts` bound to the active language and the `dates` catalog; the helpers format with `dayjs(iso).locale(locale)`, never the global dayjs locale, and require that context (calling one without it does not compile). Data files (`data/*.ts`) keep their shape and field names but hold translation keys that the consuming component passes through `t()`; values that travel in the URL or to the backend (filters, sort) never change. Helpers that are not hooks receive translated text as a parameter (`deviceLabel(device, unknownDeviceLabel)`, `downloadRecoveryCodes(codes, { locale, t })`). Proper nouns (browser and authenticator names, sample device names) stay as they are.
- **Backend texts of these pages** go through `TranslatedText::of('setting/…')`: `TrustedDeviceOperationResult::message()`, `TrustedDeviceAction::label()`, the trusted device requests and the `RequiresTwoFactorOtp`/`HasPasswordConfirmation` concerns, `TrustedDeviceService`, `TwoFactorController` and its requests, `PasswordController` and `AccountSettingsController::update()`. `TrustedDeviceDashboardCache::recentActivity()` relabels the cached rows on every read, since the cache is shared by every language. `PasswordNewController` and `PasswordResetLinkController` no longer force `'es'`.
- **Tests** — `tests/Feature/Http/SetApplicationLocaleTest.php` and `HandleInertiaRequestsLocaleTest.php`; `tests/Feature/Translation/FrontendTranslationsTest.php`, `SettingPageTranslationsTest.php` (each settings page shares exactly its groups, and changing the language in Profile shows the next page in it), `SettingTranslationKeysTest.php` (same keys, non-empty texts and same placeholders in `en` and `es` for `setting/*`, `dates` and `validation`), `FrontendTranslationKeysTest.php` (every key literal of `resources/js` names a text in both languages — this replaces typed keys, since TypeScript does not check them) and `SettingHardcodedTextTest.php` (no JSX text, text attribute or property, or Spanish literal written by hand in the translated settings folders, with an explicit list of allowed literals and their reason). Tests compare messages with `translatedTextIn(PreferredLocale, $key)` instead of copying the text, and `createUserPreferring()` creates a user in a given language. Symfony gives every test request `Accept-Language: en-us`, so a guest in a test gets English; an empty header stands for a browser that sends none.
- **Out of scope** — the other React modules (auth, home, post, comment, public profile, announcement and the Appearance page) stay in Spanish until their own tasks; posts and comments already format their **dates** with `useDateTime()`, so a user in English sees English dates there. The screen-reader texts of shared shadcn primitives (`Toggle Sidebar`, `More pages`, the dialog's `Close`) are still in English.
