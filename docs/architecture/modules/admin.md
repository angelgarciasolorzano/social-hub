# Admin panel (Filament + Spatie Permission)

The system module for the Filament admin panel and its authorization: panel structure, resources, the role and permission catalog, the Admin commands, backups, and role management from the panel (SOC-44 to SOC-75).

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

## Module and panel

**Admin** (`app/Modules/Admin/`) — system module for the Filament admin panel and Spatie Permission authorization, including the management of roles and permissions from the panel (SOC-69) and custom roles created from it (SOC-70); its provider and resource layout are documented below.

The dashboard replaces Filament's `FilamentInfoWidget` with `AdminQuickLinksWidget` (permission-filtered navigation; its Announcements link asks `AnnouncementPolicy::viewAny` through `Gate`, SOC-61) and `OperationalSummaryWidget` (permission-gated account, activity, and backup metrics). Admin data transfer objects live in `app/Modules/Admin/Data/`; `DashboardBackupSummaryData` stores backup aggregates without archive filenames, while `BackupSummaryWidget` receives listing data from `BackupManagement::getWidgetData()`.

`Admin` is a system module and exception to the standard two-provider/module-route pattern. `app/Modules/Admin/Providers/AdminPanelProvider.php` is registered in `bootstrap/providers.php`; it configures panel id `admin`, path `/admin`, guard `admin`, and discovery under `app/Modules/Admin/Filament/`. The `admin` session guard uses the existing `users` provider; `web` remains the application's default guard. Filament supplies the panel routes, so don't add duplicate routes in a module `routes/` directory.

The `admin` session guard authenticates Filament panel requests through the existing `users` provider; `web` remains Laravel's default guard for regular application authentication. Spatie also uses `admin` as the `guard_name` for Admin roles and permissions. These are separate concepts: the session guard authenticates requests, while Spatie's guard name scopes which roles and permissions apply to the `User` model.

## Resources

Keep Filament resources in the generated per-resource hierarchy under `app/Modules/Admin/Filament/Resources/<PluralModel>/`: the resource class at the directory root, and its `Pages/`, `Schemas/`, and `Tables/` in their own subdirectories as needed. The current User resource is `Users/UserResource.php`, with list/detail pages in `Users/Pages/` and the table definition in `Users/Tables/UsersTable.php`. Follow the [Filament 5 resource documentation](https://filamentphp.com/docs/5.x/resources/overview) when extending this layout. **Announcements (SOC-61)** — `Announcements/AnnouncementResource.php` (model `App\Modules\Announcement\Models\Announcement`, URL `/admin/announcements`, navigation label 'Announcements') has no `can*()` overrides: Filament asks `AnnouncementPolicy`. Its pages are `index` (`ListAnnouncements`, tabs Scheduled / Active / Expired / All on the model's date scopes, opening on Active, and a create button), `create`, `view` and `edit`; create and edit go through `AnnouncementService` with `AnnouncementData`, and the edit page's delete action too. `Schemas/AnnouncementForm` has the content (title, a `RichEditor` without attachments and with a reduced toolbar, and the image through `SpatieMediaLibraryFileUpload`, max 2 MB), the display settings and a live 'Has button' toggle that shows the button fields, whose link must be `https://` or a path of this site starting with `/` (a `//host`, `javascript:` or any space or control character, such as `/\t/host`, is rejected). **Presentation (SOC-63)** — the Display section has a `Radio` 'Show as' (`ToggleButtons` has no per-option descriptions) with the options and descriptions of `AnnouncementDisplay`, default `toast`. `type` is `live()`: choosing Critical switches it to Dialog and any other type back to Toast while the hidden, non-dehydrated `display_was_chosen` is false; touching 'Show as' sets it, and editing starts with it set, so a saved presentation never changes on its own. The dates are `live(onBlur: true)` for a non-blocking warning hint, 'N other dialog(s) are shown in the same period.', computed with `dialogsOverlapping()` without the announcement being edited. `Tables/AnnouncementsTable` preloads `creator`, shows 'Shown as' (a badge with `AnnouncementsTable::displayIcon()`) and filters by type, audience and presentation; `ListAnnouncements` adds an 'Active dialogs' tab (`running()->dialogs()`) whose warning badge counts them (one query per page load, SOC-63); its row actions are View, Edit and a group with Preview (a modal rendering `admin::filament.announcements.preview` with the sanitized body: a dialog mockup with 'Entendido' over a dimmed backdrop for a dialog, the floating card for a toast, and a line saying how it is shown, to whom and whether it comes back after closing), Duplicate (`replicate`, opens the copy) and Unpublish now (only for a running announcement, `update`). `Schemas/AnnouncementInfolist` renders the body through `safeBodyHtml()` and shows 'Shown as' with the same badge as the table. The image fields come from the official `filament/spatie-laravel-media-library-plugin` (SOC-61). **Activity log (SOC-56)** — `ActivityLogs/ActivityLogResource.php` (model `App\Modules\ActivityLog\Models\ActivityLog`, URL `/admin/activity-logs`, navigation label 'Activity log') has no `can*()` overrides: Filament asks `ActivityLogPolicy`, and only the `index` and `view` pages exist. `Tables/ActivityLogsTable` eager loads `causer` and `subject` (one query per morph type, constant for any page size), shows date, log, event (labels from `ActivityLogEventCatalog`), 'Performed by' and 'Subject', and filters by log, event (grouped by log), causer (a searchable user `Select`, since `causer` is polymorphic) and date range; the causer and date filters are the public `ActivityLogsTable::causerFilter()` and `dateRangeFilter()`, which the role history reuses (SOC-73). `Schemas/ActivityLogInfolist` has the sections Activity, Details (the stored properties without `ip`/`user_agent`, booleans as Yes/No and lists joined by commas) and Request (IP and user agent, or 'Not recorded' for console actions); for a role change (`RoleActivityChangeType::forEvent()`) the Activity section adds a 'Detail' entry with the same sentence as the role history, looking up a duplicate's source role with one query (SOC-73). Content of posts or comments is never shown; a deleted causer reads 'Deleted user #id' and a missing subject '<Type> #id (deleted)'. The user detail adds `Users/RelationManagers/ActivityLogsRelationManager` (tab 'Activity'): it reuses `ActivityLogsTable::configure()` over `ActivityLog::query()->involvingUser($owner)` (base relationship `User::causedActivityLogs()`), and shows only on `ViewUser` when the administrator may view that user and `viewAny` activity. Behavior shared by several Admin classes lives in traits under `Concerns/` (`Console/Concerns/InteractsWithAdminCatalog.php` for the three Admin commands, including the `--actor` validation, `Filament/Concerns/BuildsDailyActivityCharts.php` for the activity widgets, `Filament/Concerns/DescribesActivityLogParties.php`, which describes an activity's causer and subject by type and id (an existing role by its `displayName()`, a deleted one by type and id, SOC-73) with a link only when the administrator may open that user, post, live comment or admin role, and `Filament/Concerns/ConfirmsCurrentPassword.php` (SOC-69), the current-password field and its check, five wrong attempts per minute per administrator and action), following the repository's `Concerns/` convention; `Console/Commands/` and `Filament/Widgets/` hold only the classes that are actually registered or discovered.

## Panel access and authorization

`User::canAccessPanel()` requires the `admin` panel, a verified email, an account that is not suspended (SOC-35), and `admin.access`; `AdminPanelProvider` also requires app-based MFA. Section access is checked through permissions, so `admin.access` alone does not grant access to dashboard, Users, Posts, the activity log, Announcements, Backups, or Roles. The catalog defaults are assigned when each role is first created; use the authorization commands below for later operational changes. **Authorization lives in the model policy (SOC-57)**: resources do not override `can*()`; Filament asks the policy of the resource's model, and relation managers and widgets ask the same policy through `Gate::forUser($user)->allows('viewAny', Model::class)` / `allows('view', $record or Model::class)` instead of checking `AdminPermission` directly (only the invite action of `ListUsers` and the dashboard and Backups pieces, which have no model, still check permissions). Filament allows any ability whose method the policy does not define, so a read-only policy must deny every write ability explicitly. `UserPolicy` controls read access to User records, allows only `suspend` and `reactivate` among the writes (SOC-35, see [User](user.md)) and denies every other mutation; `ActivityLogPolicy` does the same for the activity log; `AnnouncementPolicy` (`app/Modules/Announcement/Policies/`, SOC-61) allows each panel ability with its own permission, `replicate` with `admin.announcements.create`, denies `deleteAny`, `restore`, `restoreAny`, `forceDelete` and `forceDeleteAny`, and adds the application's `dismiss`; `PostPolicy` (`app/Modules/Post/Policies/`) for posts (`viewAny` with `admin.posts.viewAny`, `view(User, ?Post)` with `admin.posts.view` and, given a post, only while it still has its author; without a post it serves the static `canView()` of widgets, and it denies `create`, `update`, `delete`, `deleteAny`, `restore`, `restoreAny`, `forceDelete` and `forceDeleteAny`). `CommentPolicy` adds the panel's `viewAny` and `view` (both `admin.posts.view`; comments have no permissions of their own) next to the application's `update`/`delete`, which let the author change their own comment, so `CommentResource` keeps every write ability (`canCreate`, `canEdit`, `canDelete`, `canDeleteAny`, `canRestore(Any)`, `canForceDelete(Any)`) pinned to `false` with a docblock explaining why: these are the only authorization overrides left in Admin resources. User's table/detail view exposes only name, email, account status (badge, plus a status filter in the table), verification/creation timestamps, and last login; keep credentials and 2FA secrets out of Filament output. `ViewUser` has the header actions 'Suspend account' and 'Reactivate account' (confirmation modal with a required 'Reason', authorized with `->authorize('suspend'|'reactivate')`, calling `AccountStatusService`; when another tab changed the status while the modal was open, `ViewUser::callMountedAction()` sends the action's failure notification ('already suspended' / 'already active') and closes the modal without writing, because Filament's own re-check of the policy would otherwise drop the call silently), and the read-only 'Status history' tab (`Users/RelationManagers/AccountStatusChangesRelationManager`: date, status, reason and 'Changed by', or 'Deleted user'). Badge label, color and filter options come from `Filament/Concerns/DescribesAccountStatus.php`.

## Users, Posts and dashboard pages

- `UserResource` shows `name`, `email`, `email_verified_at`, `created_at` and `last_login_at`, never passwords or 2FA secrets and codes. `ViewUser` adds the `UserActivityOverview` widget (posts, comments and active trusted devices, with daily post and comment trends over the last seven days).
- The user detail has read-only relation managers scoped through `UserPolicy`: `PostsRelationManager` (search, sort, filter by comments and date, opens the shared Posts detail), `ActivityLogsRelationManager` (also requires `admin.activity.viewAny`), `TrustedDevicesRelationManager` (device name, browser/OS summary, last use, expiry and derived state; it selects an allowlist of columns and never exposes `token_hash`, the IP or the raw `user_agent`), plus the status history and roles tabs described above.
- `PostResource` is read-only: author, dates and content, and `CommentsRelationManager` with paginated comments whose replies load when a comment's detail opens.
- Dashboard widgets live in `Filament/Widgets/`: `RegistrationSummaryWidget` (accounts and verified accounts with seven-day trends) and `RegistrationsChart` (sign-ups over 7, 30 or 90 days or 12 months, grouped by day, week or month, with an empty state), next to `AdminQuickLinksWidget` and `OperationalSummaryWidget`.
- `AdminServiceProvider` registers the module's Artisan commands. Spatie's published migration stays in the global `database/migrations/`; Admin's own code, seeders and tests stay in the module. Tests live in `app/Modules/Admin/Tests/`, Filament resource tests mirror the resource, page and relation-manager structure, and dashboard tests are grouped under `Tests/Filament/`.

## Database backups (SOC-55)

**Database backups (SOC-55)** use Spatie Backup behind the custom Filament page at `/admin/backups`; this feature does not use the Filament backup plugin or MediaLibrary. The separate `admin.backups.create` and `admin.backups.download` permissions protect queueing and password-confirmed downloads; the reader role grants view access only. The page has no manual delete or restore action. The `backups` disk (`config/filesystems.php`, private, `throw`/`report` on) keeps its own bucket (`BACKUP_S3_BUCKET`) while its credentials and connection fall back to `AWS_*` (SOC-62): `env('BACKUP_S3_ACCESS_KEY_ID', env('AWS_ACCESS_KEY_ID'))` and the same for the secret, region, endpoint and path style, so a defined `BACKUP_S3_*` wins (a dedicated IAM identity in production) and an absent one reuses the general value; an empty one (`BACKUP_S3_ACCESS_KEY_ID=`) defeats the fallback, which is why `.env.example` sets them to `"${AWS_...}"`. Downloads are presigned `temporaryUrl()` links built from the endpoint, so the disk has no `url` and `BACKUP_S3_URL` no longer exists. Existing administrators do not receive `admin-backups-reader` automatically; grant it explicitly with `admin:user-role grant <email> admin-backups-reader --actor=<admin-email>` when needed.

## Seeding and production bootstrap

`DatabaseSeeder` runs `AdminAuthorizationSeeder`, `AdminUserSeeder` and `AdminCustomRoleSeeder`. The authorization seeder creates the catalog under Spatie's `admin` guard and marks every `AdminRole` as a system role (`is_system = true`), also one that already existed, without touching its permissions (SOC-70). In `local` and `testing`, `AdminUserSeeder` assigns Angel (`angel@gmail.com`) the base role and all five reader roles (`AdminUserSeeder::readerRoles()`: dashboard, users, posts, activity and backups; the provisioner role is never assigned automatically; Angel also gets `admin-users-moderator` (SOC-35), `admin-backups-operator`, `admin-announcements-manager` (SOC-61), `admin-announcements-reviewer` (SOC-64) and `admin-roles-manager` (SOC-69), so those flows can be tried locally; random administrators never get them), then promotes random users until at least 20% of all users (rounded up, counting Angel and anyone already holding `admin`) are administrators; each one gets `admin` plus a random, non-empty subset (1 to 4) of the five reader roles. It preserves existing role assignments and is idempotent. In `local` and `testing`, `AdminCustomRoleSeeder` (SOC-70) then creates three sample custom roles with complete requirements, 'Soporte' (`custom-soporte`: users and activity, read only), 'Editor de contenido' (`custom-editor-de-contenido`: posts read, announcements without delete) and 'Auditor' (`custom-auditor`: activity, dashboard and backups read), each held by 1 to 3 random administrators and never by Angel; it skips a role that already exists, does nothing without the catalog and records no activity. The seeded administrators have roles but cannot enter the panel without app-based MFA, which seeders do not configure. For production bootstrap, initialize the catalog and promote an existing verified account:

```bash
php artisan db:seed --class='App\Modules\Admin\Database\Seeders\AdminAuthorizationSeeder'
php artisan admin:bootstrap-admin admin@example.com --actor=admin@example.com
```

## Admin commands

Every Admin command requires `--actor=<email>`, the person running it, who is recorded as the causer in the `admin` activity log (SOC-54). The actor must exist and be verified; for `admin:user-role` and `admin:role-permissions` it must also hold `admin.access`, while `admin:bootstrap-admin` accepts any verified actor, including the promoted user, because no administrator exists yet. A missing `--actor` answers `INVALID` and a rejected actor `FAILURE`, both without changes. Only real changes are recorded (`admin.bootstrapped` with the assigned `roles`, `admin.role_granted` / `admin.role_revoked` with the target user and `role`, `admin.role_permission_granted` / `admin.role_permission_revoked` with the `Role` as subject); a repeated grant or a revocation blocked to protect the last `admin.access` records nothing. The validation lives in `InteractsWithAdminCatalog::actorEmail()` and `resolveActor()`, which the three commands share. Since SOC-69, `admin:user-role` and `admin:role-permissions` validate their arguments and actor and then delegate the write to `AdminAuthorizationService` (see below), turning each `AdminAuthorizationFailure` into their own console message (`InteractsWithAdminCatalog::catalogFailureMessage()`; since SOC-70 also the locked role and the missing requirements, naming the permissions to grant or revoke first); `admin:bootstrap-admin` still writes and audits on its own.

`admin:bootstrap-admin <email> --actor=<email>` runs once: it requires the authorization catalog, rejects unverified accounts, refuses a second bootstrap after `admin.access` exists, and assigns `admin` plus all five reader roles (activity and backups included since SOC-56 and SOC-55). Later, `admin:user-role <grant|revoke> <email> <role> --actor=<email>` assigns or revokes one role of the `admin` guard, system or custom (SOC-70: the role is looked up by its stored name, so `custom-soporte` works; an unknown name answers `INVALID` with the stored role names, a cataloged name not stored yet answers the uninitialized catalog); the system roles are every `AdminRole` case: `admin`, `admin-dashboard-reader`, `admin-users-reader`, `admin-users-provisioner`, `admin-users-moderator`, `admin-posts-reader`, `admin-activity-reader`, `admin-backups-reader`, `admin-backups-operator`, `admin-announcements-manager`, `admin-announcements-reviewer`, `admin-roles-reader`, and `admin-roles-manager`. `admin:role-permissions <grant|revoke> <role> <permission> --actor=<email>` changes the catalog permissions of a role of the `admin` guard, system or custom, except the locked `admin` role; valid permissions are every `AdminPermission` case: `admin.access`, `admin.dashboard.view`, `admin.users.viewAny`, `admin.users.view`, `admin.users.create`, `admin.users.suspend`, `admin.users.reactivate`, `admin.users.roles`, `admin.posts.viewAny`, `admin.posts.view`, `admin.activity.viewAny`, `admin.activity.view`, `admin.backups.view`, `admin.backups.create`, `admin.backups.download`, `admin.announcements.viewAny`, `admin.announcements.view`, `admin.announcements.create`, `admin.announcements.update`, `admin.announcements.delete`, `admin.announcements.review`, `admin.roles.viewAny`, `admin.roles.view`, `admin.roles.update`, `admin.roles.create`, and `admin.roles.delete`. Both commands reject unknown roles and permissions outside the enum, protect the last `admin.access` grant and refuse a permission set with missing requirements.

## Roles and permissions in the panel (SOC-69)

**Roles and permissions in the panel (SOC-69)** — roles and permissions can also be managed from the panel. Permissions stay closed to `AdminPermission` (none is ever created, renamed or deleted from the panel); roles are the system roles of `AdminRole` plus the custom roles of SOC-70, described in the next paragraph, which updates several details of this one. `App\Modules\Admin\Services\AdminAuthorizationService` is the only writer of the catalog outside the seeders: `grantRole` / `revokeRole` / `grantPermission` / `revokePermission` (each in its own transaction, returning whether something changed) lock the `admin` role, the `admin.access` permission and the affected rows, refuse to leave nobody with `admin.access`, record `admin.role_*` / `admin.role_permission_*` only for real changes and flush Spatie's cache after the commit; `lockCatalog()` lets the commands report an uninitialized catalog first. The panel uses `syncUserRoles()` and `syncRolePermissions()`, which apply the difference to the selected cataloged values in one transaction (grants before revocations, permissions outside the catalog and roles of other guards untouched), return `App\Modules\Admin\Data\AdminAuthorizationChanges` (`granted`, `revoked`, `hasChanges()`, `changeCount()`) and roll everything back when the acting administrator would lose `admin.access` or the permission that authorized the action. Refusals are `App\Modules\Admin\Exceptions\AdminAuthorizationException` carrying an `App\Modules\Admin\Enums\AdminAuthorizationFailure` (`catalog_not_initialized`, `role_not_initialized`, `permission_not_initialized`, `last_admin_access`, `actor_would_lose_access`) whose `message()` is the panel text. The service does not authorize: `App\Modules\Admin\Policies\RolePolicy` allows `viewAny`/`view` with `admin.roles.viewAny`/`admin.roles.view` and `update` with `admin.roles.update` (SOC-70 extends it by role type, see below); `UserPolicy::manageRoles` requires `admin.users.roles` and another user's account (nobody changes their own roles from the panel; the console still can). `Roles/RoleResource.php` (the module's `Role`, URL `/admin/roles`, navigation group 'Access control', only roles of the `admin` guard through `getEloquentQuery()`) has `ListRoles` (role name, description, permission and user counts in one query with `withCount`, search by stored or translated name, a 'Permission matrix' header action and the header widgets `RolesOverview` — administrators with `admin.access`, roles nobody holds, and authorization changes of the last 30 days with a 7-day sparkline — and `UsersPerRoleChart`, a bar per role), `ViewRole` (infolist with the role and its permissions grouped by area, and the header action 'Edit permissions': one `CheckboxList` per area with each permission's description, plus the current password; it calls `syncRolePermissions()` and notifies the change count, 'unchanged' or the failure's message), the read-only tabs `RoleUsersRelationManager` (users holding the role; see the Role users tab (SOC-75) section) and `RoleActivityLogsRelationManager` (the role's history, described in the Role history (SOC-73) section), and the resource page `RolePermissionMatrix` (`/admin/roles/matrix`, view `admin::filament.roles.permission-matrix`, permissions by area against roles, one query). In Users, `ViewUser` adds the header action 'Manage roles' (the roles of the `admin` guard with descriptions plus the current password, `->authorize('manageRoles')`, calling `syncUserRoles()`), the read-only tab `Users/RelationManagers/RolesRelationManager` and the infolist section 'Effective permissions' (the cataloged permissions the user holds through any role, by area), and `UsersTable` adds a 'Roles' badge column and a multiple 'Role' filter; all of them show only to an administrator who may `viewAny` roles. Both write actions confirm the current password through `ConfirmsCurrentPassword`. Texts live in `lang/{en,es}/admin/roles.php`: the catalog names and descriptions use the case name in snake case as key (`admin/roles.catalog.permissions.admin_users_view.label`, read through `AdminRole::label()`/`description()` and `AdminPermission::label()`/`description()`/`area()`), because permission values contain dots. A database seeded before SOC-69 gets the two new roles and four permissions by running `AdminAuthorizationSeeder` again (it never changes the permissions of existing roles), and existing administrators receive them only explicitly: `php artisan admin:user-role grant <email> admin-roles-manager --actor=<admin-email>`. Tests live in `app/Modules/Admin/Tests/{Services,Policies,Filament/Concerns,Filament/Resources/Roles}/` and next to the Users and activity log tests they extend.

## Custom roles (SOC-70)

**Custom roles (SOC-70)** — administrators create their own roles from the panel next to the system roles.

- **Model** — `App\Modules\Admin\Models\Role` extends Spatie's `Role` and is the `role` model of `config/permission.php`, so Spatie and every relation return it; nothing in `app/` uses Spatie's class except the model that extends it. The migration `app/Modules/Admin/Database/Migrations/2026_11_04_000000_add_presentation_columns_to_roles_table.php` adds `is_system` (boolean, indexed, default false; the model also defaults it in `$attributes`), `label` (`Role::LABEL_MAX_LENGTH`, 80) and `description` (`Role::DESCRIPTION_MAX_LENGTH`, 255). Scopes `admin()` (guard `admin`, `Role::GUARD_NAME`), `system()` and `custom()`; `isSystem()`, `isLocked()` (only the `admin` role of the `admin` guard), `adminRole()` (the catalog case of a system role), `displayName()` / `displayDescription()` (the translated catalog texts of a system role, the saved texts of a custom one, the stored name as last resort) and the static `inDisplayOrder()` (system roles in catalog order, then custom roles by shown name), which every list, chart, matrix and selector uses. `RoleFactory` makes a custom role by default, with `system(AdminRole)` and `withoutLabel()`. The IDE helper types these `#[Scope]` methods poorly, so code the editor reads often filters with `where('guard_name', …)` / `where('is_system', …)` instead.
- **Rules** — a custom role's `name` is `custom-` plus the slug of its label, with `-2`, `-3`… when taken, and never changes; its label is unique among the roles of the `admin` guard ignoring case. System roles can have their permissions edited but cannot be renamed or deleted. The `admin` role is **locked**: it only grants panel access, so nobody changes its permissions (it can still be assigned and removed). **Dependencies**: `AdminPermission::requires()` lists what a permission needs (a `view` needs its area's `viewAny`; suspend, reactivate and manage roles need the user list and detail; create, update, delete, review and download need their area's read permissions), `withRequirements()` adds them transitively in catalog order, `missingRequirements()` lists what a set lacks and `dependents()` what needs a permission; a role can never be left with a permission whose requirements it lacks. A custom role with users cannot be deleted.
- **Service** — `AdminAuthorizationService` now receives `Role` models everywhere (`lockCatalog(Role)`, `grantRole(User, Role, User)`, `grantPermission(Role, AdminPermission, User)`, `syncUserRoles(User, list<Role>, User)`, `syncRolePermissions(Role, …)`) and treats system and custom roles alike: the sync of a user's roles covers every role of the `admin` guard and keeps roles of other guards. It locks the `admin` role first and then the affected role by id, re-read so a deleted role answers `role_not_initialized`. New methods: `createRole(label, ?description, list<AdminPermission>, actor): Role`, `updateRoleDetails(Role, label, ?description, actor): bool`, `duplicateRole(Role $source, label, actor): Role` (the source's description, translated for a system role, and permissions) and `deleteRole(Role, actor)`; texts are trimmed and validated (`InvalidArgumentException`). New `AdminAuthorizationFailure` cases: `role_locked`, `system_role_protected`, `role_has_users` (counted inside the transaction), `role_label_taken` and `permission_dependency_missing`. New audit events, recorded only with the stored name and ids, never the label or description: `admin.role_created` (`role`, `permissions`), `admin.role_updated` (`role`, `changed_attributes`), `admin.role_duplicated` (`role`, `source_role_id`) and `admin.role_deleted` (`role`); `admin.role_*` grants and revocations now record the role's stored name, `custom-…` for a custom role.
- **Policy** — `RolePolicy` receives the module's `Role` and decides by type: `viewAny`/`view` as in SOC-69; `create` and `replicate` with `admin.roles.create`; `update` (permissions) with `admin.roles.update` for any role of the `admin` guard except the locked one; `updateDetails` with `admin.roles.update` and `delete` with `admin.roles.delete`, both only for custom roles; it denies `deleteAny`, `restore`, `restoreAny`, `forceDelete`, `forceDeleteAny` and `reorder`. The model carries `#[UsePolicy(RolePolicy::class)]`, which is how Laravel finds it; `AdminServiceProvider` no longer registers it with `Gate::policy()`.
- **Panel** — `ListRoles` adds 'New role' (label, description, the permission checkboxes, a live summary and the current password; a taken label is reported on its field) and the widget `RoleTypesOverview` (system roles, custom roles and custom roles without users in one query), after `RolesOverview`, whose 'Roles without users' and authorization changes now include custom roles and their lifecycle events. `RolesTable` shows `displayName()` with the stored name under it, a 'Type' badge ('System' / 'Custom', with a lock on `admin`), `displayDescription()`, a type filter and search by label; 'Not editable' no longer exists. `RoleInfolist` shows the lock notice on `admin`, the type and the identifier. `ViewRole` has 'Edit permissions' (policy `update`, hidden on `admin`), 'Edit details' (`updateDetails`), 'Duplicate' (`replicate`, current password, opens the copy) and 'Delete' (`delete`, current password, disabled with the number of users while the role has any, back to the list). The permission checkboxes of 'New role' and 'Edit permissions' come from `Filament/Concerns/EditsRolePermissions.php`: one live `CheckboxList` per area that checks a permission's requirements and unchecks its dependents as soon as one changes (across areas), and a live summary ('Grants N permissions: …' / 'Revokes …' / 'The permissions do not change.'). `RoleUsersRelationManager` adds 'Add users' (a searchable multiple select of users without the role, never the administrator's own account, plus the current password, one transaction) the row action 'Remove from role' (also with the current password) and, since SOC-75, the bulk action 'Remove the role', all only with `admin.users.roles` through `UserPolicy::manageRoles`. `RolePermissionMatrix` and `UsersPerRoleChart` include every role of the `admin` guard in display order. In Users, 'Manage roles', the roles column and filter and the roles tab offer every role of the `admin` guard with `displayName()`, and 'Manage roles' shows a live summary of the roles to assign and remove.
- **Data, texts and tests** — a database migrated before SOC-70 needs `php artisan migrate` (the presentation migration itself marks the existing `AdminRole` rows of the `admin` guard as system roles, so they are never treated as custom in between) and `AdminAuthorizationSeeder` run again (it also marks the system roles and creates `admin.roles.create` and `admin.roles.delete`); existing `admin-roles-manager` roles do not receive the two new permissions automatically: grant them with `admin:role-permissions grant admin-roles-manager admin.roles.create --actor=<admin-email>` (and `admin.roles.delete`). `ActivityLogSeeder` records Angel creating each custom role before granting it and never simulates permission changes on `admin`. Texts live in `lang/{en,es}/admin/roles.php` (`types`, `form`, `locked`, `summary`, the lifecycle actions, `relations.users.add|remove`, `widgets.types`, the new failures) and the event names in `admin/activity-log.php`; `AdminTranslationKeysTest` requires `types.*` and a text per failure, and `AdminHardcodedTextTest` also scans `EditsRolePermissions`. Tests: `Tests/Enums/AdminRoleManagementAuthorizationEnumsTest`, `Tests/Models/RoleTest`, `Tests/Services/AdminAuthorizationService{,Sync,RoleLifecycle}Test`, `Tests/Policies/RolePolicyTest`, `Tests/Filament/Concerns/EditsRolePermissionsTest`, `Tests/Filament/Resources/Roles/**`, `Tests/Database/{AdminCustomRoleSeederTest,AdminRolePresentationMigrationTest}` and the command, Users and activity log seeder tests.

## Role history (SOC-73)

**Role history (SOC-73)** — the 'History' tab of a role (`Roles/RelationManagers/RoleActivityLogsRelationManager`) reads like an audit of that role.
- **Query** — `Role::activityLogQuery()` returns the activity whose subject is the role (permission changes and its lifecycle), the `admin.role_granted` / `admin.role_revoked` whose `properties->role` is the role's stored `name` (they keep the user as subject) and the `admin.bootstrapped` whose `properties->roles` contains it. Grants, revocations and bootstraps count only after the last `admin.role_deleted` with the same stored name, so a custom role that reuses the name of a deleted one does not inherit its history; it never filters by the role's `created_at`, because the seeders date activity in the past. It lives on the Admin model because Admin depends on ActivityLog, not the other way round, and SOC-75 and SOC-76 reuse it.
- **Description** — `App\Modules\Admin\Enums\RoleActivityChangeType` sorts the role events into `permissions`, `users` (grants, revocations and the bootstrap) and `lifecycle` (created, updated, duplicated, deleted), with `events()`, `label()` and `forEvent()`. `Filament/Concerns/DescribesRoleActivity::roleActivityDetail()` turns an activity into one translated sentence from its event, its stored properties and its loaded subject, without queries: the permission's cataloged name, the user's name (or 'Deleted user #id'), the number of permissions a role was created with, which texts were edited, the source role of a duplicate (its name comes in a map, or 'Role #id (deleted)'); anything incomplete or foreign reads 'Change without details'.
- **Table** — `Roles/Tables/RoleActivityLogsTable` shows date, kind of change (badge, colored by kind), detail and 'Performed by' (event and subject are toggleable, hidden by default), filters by kind of change (multiple) plus the shared causer and date filters, groups by day (newest first, collapsible) and opens the activity's detail. The relation manager lists `activityLogQuery()` and loads the names of the duplicates' source roles once per page from the visible records, so rendering 10 or 50 rows runs the same queries.
- **Texts and tests** — texts live in `lang/{en,es}/admin/roles.php` under `relations.history` (`columns`, `change_types`, `filters`, `group`, `detail`); a deleted user or role reuses `admin/activity-log.parties`. Tests: `Tests/Models/RoleActivityLogQueryTest`, `Tests/Filament/Concerns/DescribesRoleActivityTest`, `Tests/Filament/Resources/Roles/RelationManagers/RoleActivityLogsRelationManagerTest` and the activity log list and detail tests.

## Role users tab (SOC-75)

**Role users tab (SOC-75)** — the 'Users' tab of a role (`Roles/RelationManagers/RoleUsersRelationManager`) is an access review of that role.
- **Grant queries** — `Role::grantActivityQuery()` returns the `admin.role_granted` of the role (by `properties->role`) after the last `admin.role_deleted` with the same stored name, the rule `activityLogQuery()` also uses (the shared private `lastDeletionOfNameQuery()`). `Role::latestGrantsFor(array $userIds)` returns the latest grant of each given user, keyed by user id, with its causer, in two queries; a user without a recorded grant is left out. `Role::latestGrantDateSubquery()` is a subquery correlated with `users.id` that gives the date of that latest grant. The three build the Eloquent builder in a variable before applying query-builder methods, so the editor keeps the Eloquent type.
- **Table** — `Roles/Tables/RoleUsersTable::configure(Table, Role, Closure $grantsByUser)` keeps name, email and status and adds 'Assigned on' (`role_assigned_at`, `RoleUsersTable::ASSIGNED_AT_COLUMN`, selected with `latestGrantDateSubquery()`, sortable, 'Not recorded' when null), 'Assigned by' (the grant's causer through `DescribesActivityLogParties`), 'Panel MFA' (an icon from `app_authentication_secret` read raw, never decrypted or shown; it is Filament's app MFA the panel requires, not the application's Fortify 2FA), 'Last sign-in' (sortable, 'Never') and 'Other roles' (badges with `displayName()` of the other roles of the `admin` guard, in display order, with `roles` preloaded); the last three are toggleable. The relation manager loads the grants of the users on the page once per request with `latestGrantsFor()`, so 10 or 50 rows run the same queries.
- **Filters** — account status, panel MFA (ternary), 'Also has the role' (multiple, the other roles of the `admin` guard by stored name, any of them), 'Assigned between' (on the latest grant only: a user granted again after the range is left out and one without a recorded grant never matches; the subquery is rebuilt with `mergeWheres` because PHPStan rejects raw SQL) and 'No sign-in in' 30, 90 or 180 days (including users who never signed in).
- **Summary** — `RoleUsersTable::holdersSummary(Role)` is the table description: how many holders lack the panel MFA, did not sign in for 90 days (or never) and are suspended, over every holder regardless of the table filters, in one aggregate query; nothing is shown when nobody holds the role.
- **Bulk removal** — the bulk action 'Remove the role' is visible with `admin.users.roles`; rows are selectable only when `UserPolicy::manageRoles` allows them (never the administrator's own account) and `authorizeIndividualRecords('manageRoles')` checks each selected record again. It asks for the current password (its own throttle prefix), calls `revokeRole()` per user inside one `DB::transaction`, so a refused removal (for instance `last_admin_access`) changes nobody and notifies the reason, records one `admin.role_revoked` per user, deselects the rows and dispatches `ViewRole::ROLE_USERS_CHANGED_EVENT`.
- **Texts and tests** — texts live in `lang/{en,es}/admin/roles.php` under `relations.users` (`columns`, `not_recorded`, `mfa`, `filters`, `bulk_remove`, `summary`). Tests: `Tests/Models/RoleGrantActivityTest`, and in `Tests/Filament/Resources/Roles/RelationManagers/` `RoleUsersRelationManagerTest` (columns and query count), `RoleUsersFiltersTest`, `RoleUsersBulkRemoveTest` and `RoleUsersSummaryTest`.
