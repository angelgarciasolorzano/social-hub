# Auth and trusted devices

Login, registration, email verification, password reset, the login 2FA challenge and trusted devices (`app/Auth/`, old architecture), with the settings pages that manage trusted devices.

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

## Backend layout

**Auth** (`app/Auth/`) — login, register, email verification, password reset (via Fortify), the login 2FA challenge, and trusted devices.

- **Feature layout**: Login, Register, Email verification, Password, and TrustedDevice live under `app/Auth/Modules/{Login,Register,Email,Password,TrustedDevice}/`. Each feature owns its applicable controllers, requests, services, listeners, and tests; shared route wiring remains in the Auth parent.
- **Shared infrastructure stays at the parent**: `app/Auth/Models/` (domain models), `app/Auth/Database/{Migrations,Factories,Seeders}/` (migrations and factories are registered automatically by `AuthServiceProvider::loadMigrationsFrom`), `app/Auth/Providers/`, `app/Auth/routes/` (one file per concern, e.g. `trustedDevice.php`), and `app/Auth/config/`.
- **Submodule convention (`app/Auth/Modules/<Feature>/`)** — established in SOC-14. The Auth submodules include `Email/`, `Login/`, `Password/`, `Register/`, and `TrustedDevice/`. A submodule mirrors the parent's *feature-side* layout (`Controllers/`, `Requests/`, `Services/`, `Listeners/`, `Resources/`, `Concerns/`, `Enums/`, `Tests/`) as applicable, but **does not duplicate providers, models, routes, migrations, or factories** — those stay shared at the parent so the feature integrates with the domain's wiring without owning its own bootstrap.
- `AuthRouteServiceProvider` loads `routes/` (one file per concern); `AuthEventServiceProvider` registers Fortify listeners owned by Auth/TrustedDevice; User registers its recovery-codes listener through `app/User/Providers/UserEventServiceProvider.php`.

## Trusted devices

- **Trusted device audit log (SOC-20)** — `app/Auth/Database/Migrations/2026_07_13_221739_create_trusted_devices_table.php` is the canonical combined migration for `trusted_devices` and the append-only `trusted_device_events` table. Events record discrete actions (`Created`, `Renewed`, `Renamed`, `Revoked`, `RevokedAll`) with a nullable `user_id` foreign key using `nullOnDelete`; device metadata is stored as a snapshot, so events do not depend on a `trusted_device_id` relation. Records are inserted via `TrustedDeviceEvent::record()` (static helper) from `TrustedDeviceService` and the `TwoFactorAuthenticationDisabled` listener; password changes and resets record bulk revocations through `PasswordTrustedDeviceRevoker`, which delegates to `TrustedDeviceService::revokeAll()`.
- **Trusted device reactivation + GDPR purge (SOC-21)** — `TrustedDevice` uses Laravel's `SoftDeletes` trait (column `deleted_at`) so revoked devices stay in the table for re-confirmation. The `reactivate` endpoint always requires a 2FA code (verified inside `TrustedDeviceService::reactivate` since SOC-45; `TrustedDeviceReactivateRequest` only checks the format) before restoring the soft-deleted row and regenerating the token. The cookie fast-path described in the project's initial SOC-21 spec was deferred to a follow-up. The `force-destroy` endpoint (`DELETE /user/trusted-devices/{device}/force`, requires password confirmation via `TrustedDeviceDestroyForceRequest`) records a final `Revoked` event for snapshot continuity then `forceDelete()`s the row. The `TrustedDevicePurge` Artisan command (`trusted-devices:purge`) is registered in `AuthServiceProvider` (only when `runningInConsole()`) and scheduled daily at 03:00 — it `forceDelete()`s soft-deleted rows older than `module.auth.trusted_devices.purge_after_days` (default 90).
- **Trusted device activity log dialog (SOC-22)** — `TrustedDeviceController::activity()` returns a standard `LengthAwarePaginator` (`paginate()`, not cursor pagination) over `trusted_device_events`, sanitized against whitelists via the shared `parseMultiFilter()` helper (also used for `status`/`browser`/`lastAccess` in `extractFilters()`): `action` and `since_days` are both comma-separated multi-select filters (`since_days` values `7|30|90|180|365`, applied as an OR'd multi-cutoff — `orWhere('created_at', '>=', now->subDays($days))` per selected value, same pattern as `lastAccess`); `null` on either means no filter, not a silent default. `search` is a case-insensitive `LIKE` against the denormalized snapshot columns `device_label`, `ip`, `device_os_name` (no join needed). `index()` exposes `activity()`'s result as a single `activityDialog` prop wrapped in `Inertia::optional()` — never sent on a standard visit, only resolved when the dialog fires a partial reload requesting it — so the two payload halves (`activityLog`/`activityFilters`) stay one prop instead of two independently-resolved `Inertia::optional()` closures that would otherwise call `activity()` twice per request.
- **Trusted device controller → service split (SOC-37)** — `TrustedDeviceController` only handles HTTP: authorization, the `401` user narrowing, the `404` for non-revoked devices, cookie queueing and the flash. All state changes live in `TrustedDeviceService` (`register`, `rename`, `renew`, `revoke`, `forceDelete`, `reactivate`, `revokeAll`); each runs in a `DB::transaction`, records its `TrustedDeviceEvent`, and invalidates `TrustedDeviceDashboardCache` through `DB::afterCommit` (single private `recordEvent()` / `invalidateDashboardAfterCommit()` entry points). The service is the only reader of `module.auth.trusted_devices.cookie_lifetime_minutes` for renew/reactivate/create. `reactivate(User, TrustedDevice, string $otpCode, Request)` returns the raw token so the controller queues the cookie; `register()` returns a `TrustedDeviceOperationResult` and, when another request registers the same fingerprint between the pre-check and the `lockForUpdate` re-check, returns `AlreadyActive` (error flash, no cookie).
- **Trusted device result enum + authorization (SOC-37)** — `TrustedDeviceOperationResult` is the single enum for the controller's flash outcomes (`Created`, `AlreadyActive`, `AlreadyRevoked`, `Renamed`, `Renewed`, `Revoked`, `RevokedAll`, `Reactivated`, `ForceDeleted`, `TwoFactorRequired`) and exposes `isSuccessful()`, `message()` and `payload()` (the array handed to `Inertia::flash()`); `register()` and `renew()` are the methods that return it. Ownership is enforced by `TrustedDevicePolicy` (`app/Auth/Modules/TrustedDevice/Policies/`), registered with `#[UsePolicy]` on the model (Laravel's naming-based discovery would not find it under `Modules/`) and applied in the controller with the `#[Authorize('<ability>', 'trustedDevice')]` method attribute (`update` for update/renew, `delete`, `restore` for reactivate, `forceDelete`). The attribute runs as middleware after route-model binding, so authorization precedes FormRequest validation.
- **Trusted device enrollment hardening (SOC-45)** — "Active 2FA" means `User::hasEnabledTwoFactorAuthentication()` with Fortify's `confirm` option on (`two_factor_secret` and `two_factor_confirmed_at` both set); a pending secret never counts. `TwoFactorCodeVerifier` (`app/Auth/Modules/TrustedDevice/Services/`) is the single verifier: `hasConfirmedTwoFactor()`, `verifyTotp()`, `consumeRecoveryCode()` and `verifyCode()` (six digits are a TOTP, anything else is a single-use recovery code). The recovery-code part must run inside the caller's `DB::transaction`: it re-reads the user with `lockForUpdate` and consumes the code through `User::replaceRecoveryCode`, which removes it, so a code is single-use even under concurrent requests. Nothing it logs or returns contains codes or secrets. The login only skips the OTP with a valid, non-revoked, non-expired cookie of an account with confirmed 2FA (`TrustedDevice::validateAndTouch` checks it too); the cookie is the only credential and IP/User-Agent stay metadata. `TrustedDeviceInvalidate` is registered for both `TwoFactorAuthenticationDisabled` and `TwoFactorAuthenticationConfirmed` and revokes every device, so a cookie issued before confirmation can never bypass the OTP. There is deliberately no data migration for historical rows (nothing was in production when SOC-45 landed): revisit that before deploying with real data. `store` and `renew` require a current TOTP in `otp_code`: `TrustedDeviceStoreRequest` and `TrustedDeviceRenewRequest` share the `RequiresTwoFactorOtp` concern (error `two_factor` when 2FA is not confirmed, error `otp_code` when the code is missing or wrong; recovery codes are deliberately not accepted here: you already have a session and your authenticator at hand, whoever lacks it can sign in with a recovery code and tick remember-this-device, and every use would burn one of the 8 codes that are the backup against losing the phone), and `TrustedDeviceService::register()` / `renew()` repeat the check inside the transaction with the user row locked (returning `TwoFactorRequired`) so disabling 2FA concurrently cannot leave an active device behind. `reactivate()` verifies the code inside its transaction through `verifyCode()` (a TOTP or a recovery code consumed there), throws `ValidationException` (`two_factor` / `otp_code`) and rolls the consumption back if a later step fails. Disabling 2FA also accepts a TOTP or a recovery code: `TwoFactorDisableRequest` (User module) checks the format and verifies with the same `verifyCode()`; the recovery codes are wiped by the disabling anyway. Remembering the browser at login no longer adds a second row: `TrustedDeviceRemember` only calls `TrustedDeviceService::rememberAfterTwoFactorChallenge()`, which in one transaction reuses the latest row of the same fingerprint (user, user agent, system and IP) in any state through `TrustedDevice::findLatestForFingerprint()` — restoring it with a new token and an event `Reactivated` if it was revoked, `Renewed` if it was active or expired — and creates one with `Created` only for a browser never seen; before, revoking a device and signing in again with remember left the revoked row and a new active one (two devices for one browser). The four routes that check a two-factor code (`store`, `renew`, `reactivate` and the 2FA disable `destroy`) share one `throttle:two-factor-code` budget, defined in `FortifyServiceProvider` (5 per minute per user, per IP as a fallback), so alternating between them does not multiply the guesses a hijacked session can try (tested in `TrustedDeviceCodeThrottleTest`). Fortify rejects a replayed TOTP, so tests that reuse a code call `allowOtpReuse()` (`tests/Pest.php`). A test that sends a wrong code for a user with a TOTP secret uses `invalidOtpFor($user)`, which never matches a code of Fortify's verification window; a fixed `'000000'` would be the valid code about once in a million runs. Frontend: `TrustedDeviceIndexController` and `TwoFactorController::index` send a `twoFactorStatus` prop (`App\User\Modules\TwoFactor\Enums\TwoFactorStatus`: `disabled`, `pending`, `confirmed`) that `TrustedDeviceAddDialog` reads from the page props to show either a notice linking to the TwoFactor page or the OTP field; `TwoFactorOtpField` (six digits) and `TwoFactorCodeField` (the six digits or a recovery-code input, with a link to switch; it clears the value and the errors when switching and its mode resets when the dialog closes) live in `modules/setting/shared/components/`: the add and renew dialogs use `TwoFactorOtpField` (TOTP only), while `TrustedDeviceReactivationDialog` and the disable-2FA dialog (`DisabledTwoFactorDialog`, field `code`) use `TwoFactorCodeField`. The copy states that remembering a browser is a temporary convenience, not an independent second factor.

## Models

- `App\Auth\Models\TrustedDevice` — resolves `TrustedDevicePolicy` via `#[UsePolicy]`; has `events()` (HasMany to `TrustedDeviceEvent`); column `expires_at` drives `isActive` cast; uses `SoftDeletes` trait since SOC-21 (column `deleted_at`), so `revoke` is a soft delete and `force-destroy` removes the row permanently. Static helpers: `findActiveMatch()` and `validateAndTouch()` filter `whereNull('deleted_at')` explicitly (defense in depth), and `validateAndTouch()` also returns `false` unless the user has confirmed 2FA (SOC-45); `findLatestForFingerprint()` returns the latest row of a fingerprint in any state (active, expired or revoked) for the login remember flow, unlike `findAnyMatchForFingerprint()`, which the manual `store()` uses to answer `AlreadyActive` / `AlreadyRevoked`; `pruneOlder()` also excludes soft-deleted rows so they survive a subsequent `store()` of the same fingerprint. Scopes `#[Scope] active()` / `inactive()` filter by `expires_at` for the legacy single-table UI.
- `App\Auth\Models\TrustedDeviceEvent` — append-only audit log row. Casts `action` to `TrustedDeviceAction` enum. Relation: `user()` (nullable BelongsTo, nullOnDelete); device metadata is kept in snapshot columns instead of a device relation. Always created via `TrustedDeviceEvent::record(...)` helper, which also dispatches `TrustedDeviceEventRecorded` inside the caller's transaction (SOC-54, mirrored by the ActivityLog module).
- `App\Auth\Modules\TrustedDevice\Enums\TrustedDeviceAction` — cases `Created`, `Renewed`, `Renamed`, `Revoked`, `RevokedAll`, `Reactivated` (SOC-21 — emitted when a soft-deleted device is restored; no `Expired` in v1 — see SOC-20 follow-ups).

## Frontend

- `modules/setting/` has sub-modules mirroring PHP: `modules/accountSettings/`, `modules/trustedDevice/`, `modules/twoFactor/`, plus `shared/` (cross-module code). The `setting` module also has its own `shared/` layer (`resources/js/modules/setting/shared/{components,layouts,utils}/`) for code reused by ≥2 sub-modules — when a util is used by only one sub-module it stays private; when both consume it, promote to `setting/shared/utils/`.
- **TrustedDevice as parallel module** (SOC-20; folder/file naming and internal structure standardized in SOC-23): the dedicated `/setting/trusted-devices` view lives in `modules/setting/modules/trustedDevice/` (singular, matching the backend module `app/Auth/Modules/TrustedDevice/`; not under `modules/twoFactor/`). It mirrors the layout: `components/dialog/` split into `actions/` (11 dialogs covering device CRUD and the status dialogs tied to those actions — `TrustedDeviceAddDialog`, `TrustedDeviceRenameDialog`, `TrustedDeviceRenewTrustDialog`, `TrustedDeviceRevokeDialog`, `TrustedDeviceRevokeAllDialog`, `TrustedDeviceForceDestroyDialog`, `TrustedDeviceReactivationDialog`, `TrustedDeviceAlreadyRegisteredDialog`, `TrustedDeviceDetailsDialog`, `TrustedDeviceExpiredDialog`, `TrustedDeviceRevokedDialog`) and `info/` (3 generic/informative dialogs — `TrustedDeviceSummaryDialog`, `TrustedDeviceRecommendationsDialog`, and `TrustedDeviceActivityDialog`, moved here since it doesn't fit `actions/` and is informative rather than a CRUD flow — see SOC-22 entry below for its own internal split), with only the `index.ts` barrel left loose at the `dialog/` root; `components/ui/` (TrustedDeviceSummaryCard, TrustedDeviceMetadataItem, TrustedDeviceActivityTimeline); `components/table/` split into `trustedDevicePage/` (`TrustedDeviceTable`, `TrustedDeviceTableToolbar`, `TrustedDevicePagination` — singular, one file per component) and `trustedDeviceActivityDialog/` (pieces extracted from the activity dialog, see below); `data/`, `types/`, `utils/`. The 7 original dialogs were relocated from `modules/twoFactor/components/dialog/trustedDevice/` to enforce single ownership of domain-specific UI. The dedicated `/setting/trusted-devices` page renders the active/inactive table plus a `<Collapsible>` "Dispositivos revocados" section (SOC-21) that lists soft-deleted rows with "Re-confiar" and "Eliminar definitivamente" actions. `types/trustedDevicePreview.ts` holds `TrustedDevicePreview` (renamed from `devicePreview.ts`'s `DevicePreview` in SOC-23); `types/trustedDeviceActivityDialog.ts` holds the activity-dialog-only shapes `TrustedDeviceActivityFilters`, `TrustedDeviceActivityEvent`, `TrustedDeviceActivityPagination` (extracted out of `types/trustedDevice.ts`, which keeps only the generic model shapes); `TrustedDevicePagination` and `TrustedDeviceActivityPagination` are both type aliases of the shared `LengthAwarePagination<T>` (`resources/js/shared/types/lengthAwarePagination.ts`, added in SOC-23).
- **Trusted device activity dialog + filter-hook pattern (SOC-22; internal split + moved to `dialog/info/` in SOC-23)** — `components/dialog/info/TrustedDeviceActivityDialog.tsx` replaced an earlier infinite-scroll/cursor-pagination design with standard page pagination plus a toolbar: a search `InputGroup` with a conditional clear button (`InputGroupButton` inside a trailing `InputGroupAddon`, shown only when the field is non-empty) and a `Funnel`-triggered `Popover` holding the Acción/rango-temporal comboboxes and a reset action, mirroring `TrustedDeviceTableToolbar`'s `TrustedDeviceFiltersPopover`. SOC-23 cut the file from ~650 to ~195 lines by extracting its pieces into `components/table/trustedDeviceActivityDialog/`: `TrustedDeviceActivityPagination.tsx` (the pagination control + its 3 sub-buttons), `TrustedDeviceActivityFiltersPopover.tsx` (the filters popover), `TrustedDeviceActivityFilterCombobox.tsx` (the generic combobox the popover renders per filter), and `TrustedDeviceActivityEventList.tsx` (the event list including its empty states, plus the row component `ActivityEventRow`) — the dialog file itself now only owns the outer `Dialog`/loading-state wiring and composes these pieces. Pagination uses `<Button onClick>` handlers calling `router.reload`, not `<Link href>`, since an Inertia visit to a URL would replace the page's component tree and reset the dialog's local `open` state (closing it). **Dialogs never mutate the browser URL** — unlike a full page's toolbar (`useTrustedDeviceFilters.ts`, which legitimately uses `router.get()` so filters are shareable/bookmarkable), a dialog's filters are ephemeral UI state, so `useTrustedDeviceActivityFilters.ts` uses `router.reload({ data, only: [...], preserveUrl: true, replace: true })` instead — same debounced-search / immediate-other-fields effect pair, just a different transport. Both hooks also expose `committedFilters` (a snapshot updated only inside `triggerReload`, i.e. the instant a request is actually sent) separately from the live `filters` state: any UI that must stay in sync with the currently-*rendered* data — e.g. `hasActiveFilters` driving the empty-state copy in `TrustedDeviceTable.tsx` and the dialog — must read `committedFilters`, not `filters`, or it flashes the wrong empty-state message during the search debounce window (the input clears instantly; the still-filtered stale data doesn't arrive for another ~500 ms+). The dialog is split into an outer component (reads `usePage()` for the `activityDialog` prop, shows a `LoaderCircle` spinner while it's `undefined`) and an inner `TrustedDeviceActivityDialogBody` that only mounts once the payload arrives, so `useTrustedDeviceActivityFilters` never has to handle an unseeded initial state. **React StrictMode (`strictMode: true` in `app.tsx`) double-invokes mount effects in dev** — any "skip on first render" guard must flip its ref only inside the real user-facing setter (`updateFilter`/`resetFilters` set `hasInteractedRef.current = true`; the dialog's own fetch effect sets `hasRequestedActivityRef.current = true` right before firing), never inside the effect's early-return branch itself, or the second simulated pass reads the flag already flipped and fires a spurious reload. Both `useTrustedDeviceActivityFilters.ts` and `useTrustedDeviceFilters.ts` follow this `hasInteractedRef` pattern.
