# System announcements

Announcements that administrators publish from the Filament panel and the application shows as a toast or a dialog (SOC-61, SOC-63, SOC-64).

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

## Backend

**Announcement** (`app/Modules/Announcement/`) — system announcements that administrators publish from the Filament panel and that the application shows to its users as a toast or a dialog (SOC-61, approval workflow in SOC-64, presentation in SOC-63); `Controllers/`, `Data/`, `Database/{Factories,Migrations,Seeders}/`, `Enums/`, `Models/`, `Policies/`, `Providers/`, `Requests/`, `Resources/`, `Services/`, `Tests/`, `routes/`; namespace `App\Modules\Announcement\…`. No real-time delivery: announcements reach the user on their next page visit.

- **Persistence** — `AnnouncementServiceProvider` (registered in `bootstrap/providers.php`) loads the module migrations (`2026_10_27_000000_create_announcements_tables.php` and SOC-63's `2026_10_28_000000_add_display_to_announcements_table.php`) and registers `AnnouncementRouteServiceProvider`. `announcements` holds `title` (`Announcement::TITLE_MAX_LENGTH`, 120), `body` (the rich editor HTML, stored as written), `type` (`AnnouncementType`: `info` / `warning` / `critical`, with `label()` and `severity()`), `audience` (`AnnouncementAudience`: `all` / `authenticated` / `without_two_factor`), `display` (`AnnouncementDisplay`: `toast` / `dialog`, with `label()` and `description()`, default `toast`, SOC-63), `starts_at`, nullable `ends_at` (no end), optional `button_label` (`BUTTON_LABEL_MAX_LENGTH`, 40) and `button_url`, `is_dismissible` (default true) and `created_by` (`nullOnDelete`). `announcement_dismissals` (`announcement_id` and `user_id` both `cascadeOnDelete`, unique together) records who closed which announcement. The optional image lives in the MediaLibrary collection `announcement_image` (`singleFile()`), morph `announcement`.
- **Visibility** — one date rule in three scopes, `scheduled()`, `running()` (started, and without end or ending later) and `ended()`, mirrored in memory by `isRunning()`. `availableTo(?User)` adds the audience (a guest belongs only to `all`; a user with confirmed 2FA, `hasEnabledTwoFactorAuthentication()`, does not belong to `without_two_factor`, a pending setup still does), and `visibleTo(?User)` also drops what that user dismissed, orders by `severity()` and then the most recent start, and keeps `Announcement::MAX_VISIBLE` (3). `visibleTo` is the only source of what the application shows; the admin tabs use the same scopes. `dialogs()` keeps the dialogs, and `dialogsOverlapping(CarbonImmutable $startsAt, ?CarbonImmutable $endsAt, ?int $exceptId)` the dialogs whose schedule crosses the given one (a missing end runs forever), leaving out ended dialogs and the given announcement; it does not compare audiences, because every pair of audiences shares viewers (SOC-63).
- **Writing and audit** — `AnnouncementService` is the only writer outside factories: `create`, `update` (does nothing and records nothing without a real change), `unpublish` (sets `ends_at = now` on a running announcement; `LogicException` when it has not started or already ended), `duplicate` (copies the content and image as a new announcement starting tomorrow without end date, so it is never shown before someone reviews it) and `delete`. Each runs in a transaction and records `admin.announcement_created|updated|unpublished|duplicated|deleted` (`ActivityLogAdminEvent`) with the announcement as subject and only ids (`changed_attributes`, `source_announcement_id`), never the title or body. It does not authorize: `AnnouncementPolicy` does. `AnnouncementData::fromFormState()` turns the admin form state into typed data, drops the button when `has_button` is off and reads `display` as a value or an enum case, `Toast` when it is blank (`blank()`, since `Fluent::filled()` casts an enum to string). Changing only the presentation is audited as `changed_attributes = ['display']`, and `duplicate()` copies it.
- **Rendering** — `Announcement::safeBodyHtml()` passes the body through Filament's `RichContentRenderer`, which sanitizes it (no scripts, event handlers or `javascript:` links); every place that renders the body (the admin detail, the preview and the application) uses it, never the raw column.
- **Application** — `HandleInertiaRequests::share()` adds a lazy `announcements` prop: `visibleTo($request->user())` with `media` preloaded, serialized by `AnnouncementBannerResource` (`id`, `title`, `bodyHtml`, `type`, `display`, `buttonLabel`, `buttonUrl`, `isDismissible`, `imageUrl`; never the author, audience or dates; since SOC-63 `isDismissible` is the stored value for guests too, because the browser keeps a guest's closes). `POST announcements/{announcement}/dismiss` (`announcements.dismiss`, `auth`+`verified`, `throttle:20,1,announcements.dismiss`) is served by `AnnouncementDismissalController::dismiss` (the module's single controller, which also has `sync`, SOC-63; its routes are grouped with `Route::controller()->prefix('announcements')` like the comment ones), authorized by `#[Authorize('dismiss', 'announcement')]` (a dismissible announcement available to that user, through `availableTo`, so repeating it is allowed), stores the dismissal with `insertOrIgnore` and answers JSON `{dismissed: true}`. `POST announcements/dismissals` (`announcements.dismissals.sync`, `auth`+`verified`, `throttle:10,1,announcements.dismissals.sync`, SOC-63) is `AnnouncementDismissalController::sync`: `AnnouncementDismissalSyncRequest` (`HasFluentRules`) accepts `announcement_ids`, a list of 1 to `MAX_ANNOUNCEMENT_IDS` (20) distinct positive integers; the controller keeps only the ones `Gate::allows('dismiss', …)`, stores them with `insertOrIgnore` and answers `{dismissed: int[]}`, skipping without error the ones that ended or changed since a guest closed them. **Closing rules (SOC-63)** — every toast and every dialog can be closed: a signed-in user's close of a dismissible announcement goes to `announcements.dismiss` (it never comes back, on any device); a guest's close of a dismissible announcement stays in `localStorage` (it never comes back in that browser) and is sent to `sync` once the guest signs in; a close of a non-dismissible announcement stays in `sessionStorage`, so 'not dismissible' means it comes back in the next browser session. Dismissals are not audited.
- **Seeding** — `AnnouncementSeeder` (after `AccountStatusSeeder` in `DatabaseSeeder`) creates, through the factory, five fixed announcements in Spanish (a running warning for everyone, the critical one for `without_two_factor` with a button to `/setting/two-factor-authentication` (`AnnouncementSeeder::TWO_FACTOR_TITLE`), a running one that cannot be dismissed, a scheduled one and an expired one), then one announcement per text of `SAMPLE_ANNOUNCEMENTS` (15, each title unique; critical ones are dialogs, the rest toasts, and the fixed 2FA one is a dialog since SOC-63) with a random schedule (running 30%, scheduled 20%, ended 35%, unpublished 15%) and real dates over the last 55 days, about 30% of them edited (`updated_at` after `created_at`), and three duplicates made like `duplicate()` (same content and presentation, starting the day after the copy, no end date): about 27 rows. An unpublished one keeps `ends_at` equal to `updated_at`, as `unpublish()` leaves it. Buttons point to existing pages or to `https://example.com`. Authors are Angel (half of the time when he is an administrator) or a random administrator, or nobody without the authorization catalog. It records no activity and does nothing when `announcements` has rows; `ActivityLogSeeder::seedAnnouncementActivity()` then derives the audit from those rows: `admin.announcement_duplicated` (with `source_announcement_id`) for a later announcement with the same title and body as an earlier one, `admin.announcement_created` for every other one, `admin.announcement_unpublished` when `ends_at` equals `updated_at` and `admin.announcement_updated` (a plausible `changed_attributes`, `['display']` included) when `updated_at` is later than `created_at`, each at that date with the author as causer. Deletions cannot be derived, since the row is gone. `ActivityLogSeeder::seedAnnouncementReviewActivity()` also mirrors each seeded review row as a submitted, approved or rejected event with its actor and review ID, without content or comments.
- Tests live in `app/Modules/Announcement/Tests/{Enums,Database,Models,Queries,Policies,Data,Services,Resources,Props,Crud,Seeders}/` (suite `Announcement`), and the Filament ones in `app/Modules/Admin/Tests/Filament/Resources/Announcements/`.

- `App\Modules\Announcement\Models\Announcement` — implements `HasMedia` (collection `announcement_image`, `singleFile()`), morph `announcement`, resolves `AnnouncementPolicy` through `#[UsePolicy]` (SOC-61). Casts `type` and `audience` to their enums and the dates to immutable datetimes; has `creator()` (nullable after the author is deleted), `dismissedBy()` (BelongsToMany to `User` through `announcement_dismissals`), the scopes `scheduled`, `running`, `ended`, `availableTo`, `visibleTo`, `dialogs` and `dialogsOverlapping`, `isRunning()` and `safeBodyHtml()`, and casts `display` to `AnnouncementDisplay` (SOC-63). `AnnouncementFactory` defaults to a toast and has the states `scheduled()`, `active()`, `expired()`, `ofType()`, `forAudience()`, `withButton()` (an `https://` link), `notDismissible()`, `asDialog()` and `createdBy()`.

## Approval workflow (SOC-64)

Announcements move through `draft` → `in_review` → `approved` or `rejected`; a rejected announcement can be resubmitted, and a content or image change to an approved announcement starts a new review. `Announcement::visibleTo()` exposes only approved announcements, then applies audience, dismissal, severity ordering and the three-item limit. The append-only `announcement_reviews` table records `submitted`, `resubmitted`, `approved` and `rejected` actions with their actor and optional comment. `AnnouncementPolicy::submit()` allows only the announcement's author to submit their draft or rejected announcement; `review()` requires `admin.announcements.review`, `in_review`, and an actor who is neither the author nor the latest submitter.

`admin-announcements-reviewer` grants only `admin.announcements.viewAny`, `admin.announcements.view` and `admin.announcements.review`; it grants no create, update or delete permission. In local/testing, AdminUserSeeder assigns this role to Angel so the workflow can be exercised. Existing production administrators are not granted it automatically; add it without changing their other roles with `php artisan admin:user-role grant <email> admin-announcements-reviewer --actor=<admin-email>`.

Submissions notify eligible reviewers and decisions notify the announcement author through Filament database notifications. They are loaded by the panel, not delivered in real time or by email. Approval comments are optional; rejection comments are required. Comments remain in review history and decision notifications and are never copied to activity log properties. Activity events use `admin.announcement_submitted`, `admin.announcement_approved` and `admin.announcement_rejected`; `ActivityLogSeeder` derives seeded review events from `announcement_reviews` and includes the review row ID, actor and announcement without its comment or content.

`AnnouncementSeeder` keeps its existing running, scheduled, ended and unpublished samples approved, and adds a draft, a pending example with submission history, and approved and rejected examples with matching submit and decision history. Only approved announcements are visible to application users.

## Frontend

- **Announcements (SOC-61, SOC-63)** live in `modules/announcement/`: `types/announcement.ts` (`Announcement`, the shape of `AnnouncementBannerResource`, plus `AnnouncementType` and `AnnouncementDisplay`, mirrors of the backend enums: change them together), `utils/announcementDismissalStorage.ts`, `hooks/` (`useAnnouncementDismiss`, `useGuestDismissalSync`) and `components/` (`SystemAnnouncements`, `AnnouncementToast`, `AnnouncementDialog`, `AnnouncementContent`); `SharedData.announcements` is typed in `shared/types/index.d.ts`. `SystemAnnouncements` is mounted once in `withApp` (`app/app.tsx`), beside `FlashToaster`, so it shows on every page, guests included. `withApp` wraps the app from outside the context `usePage()` needs, so it takes the first announcements and the session state (`isAuthenticatedPage()`, `auth.user`) from `withApp`'s `page` argument and later ones from the router's `navigate` event. Toasts go to its own Sonner `Toaster` (`id="announcements"`, top center, collapsed with `expand={false}`), separate from the flash toaster (top right, no id: Sonner only shows toasts whose `toasterId` matches): each is a persistent toast (`duration: Infinity`, no swipe) with a fixed id, updated in place and closed when the announcement leaves the list, the most severe on top; a toast floats above every layout, including the fixed sidebar of `SettingLayout`. Dialogs show one at a time, the first of the server's order (the most severe first), and closing one shows the next; toasts wait while a dialog is open, because Sonner's z-index would draw them above the dialog's backdrop. `AnnouncementContent.tsx` holds what both share (`AnnouncementBody`, the sanitized `bodyHtml` through `dangerouslySetInnerHTML`; `AnnouncementButton`, Inertia's `Link` for a path of this site and a new tab with `rel="noopener noreferrer"` for an external address, with an `onAction` that runs before following it; and `announcementTypeStyles`, colors from the Tailwind palette with `dark:` variants and an icon per type). `AnnouncementToast` uses `role="alert"` only for critical ones and always shows its close button. `AnnouncementDialog` is shadcn's `Dialog` (without its corner X, whose screen-reader text is English) tinted by type; 'Entendido', `Esc`, the backdrop and the announcement's own button close it, and the body goes in `DialogDescription asChild` over a `<div>`, since the body brings its own `<p>` and lists. `useAnnouncementDismiss(initialAnnouncements, initialIsAuthenticated)` applies the closing rules of the module (server through `useHttp` with `optimistic` and a Sonner error toast for 429 and network failures, `localStorage` for a guest, `sessionStorage` for a non-dismissible one), filters what the browser closed before showing anything, and returns `toastAnnouncements` and `dialogAnnouncements`. `useGuestDismissalSync(isAuthenticated)` sends the guest's closes (at most 20) to `sync` once per sign-in through `useHttp` with `transform()`, clears them on success and keeps them for the next page load on failure, without a toast; a ref keeps StrictMode from sending twice. The storage util guards every access (no `window`, a blocked or full storage, a tampered value) and its writers return whether they stored, so no `catch` is empty.
- A floating toast was chosen over an in-flow banner because it floats above every layout, including the fixed sidebar of `SettingLayout`.
- The backend applies `status = approved` in `Announcement::availableTo()` before sharing the prop, and `AnnouncementBannerResource` carries no `status` or review history: React never models `draft`, `in_review`, `approved` or `rejected`, it receives approved announcements only and uses `display` to choose a toast or a dialog.
- An announcement button's `onAction` is how the dialog counts following the button as closing it.
