# Friendship

Friend requests and friendships (SOC-83 and SOC-84, epic SOC-82): one row per pair of users, a service that is the only writer, a policy, JSON endpoints, a people search page and a friends page with infinite scroll, the friendship data of the profile, the sidebar props and a seeder.

> Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

**Friendship** (`app/Modules/Friendship/`) replaced the old `app/Friendship/` module, written when the project started (it blocked a receiver for everybody once anyone had sent them a request, and its search sent whole `User` models, emails included, through a flash). Layout: `Controllers/`, `Database/{Factories,Migrations,Seeders}/`, `Enums/`, `Events/`, `Models/`, `Policies/`, `Props/`, `Providers/`, `Requests/`, `Resources/`, `Services/`, `Tests/`, `config/` and `routes/`; namespace `App\Modules\Friendship\…`. `FriendshipServiceProvider` merges `config/friendship.php` as `module.friendship`, loads the module migrations and registers `FriendshipRouteServiceProvider`.

## Data model: one row per pair

- **`friendships`** — `requester_id` and `receiver_id` (both `cascadeOnDelete`), `status` (`FriendshipStatus`: `pending` / `accepted`), `accepted_at`, timestamps, and two **virtual** generated columns, `user_low_id = LEAST(requester_id, receiver_id)` and `user_high_id = GREATEST(…)`, unique together. Whoever sends the request, a pair of users has one row at most: A→B and B→A cannot coexist, and a double click or two tabs cannot duplicate a request, because the database refuses the second insert.
- **Why virtual and not stored.** MySQL rejects `ON DELETE CASCADE` on the base columns of a *stored* generated column (error 1215). An indexed *virtual* column keeps both the unique pair and the cascade. The alternatives were two rows per friendship (two rows to keep in sync and no database guarantee against crossed requests) or ordering the pair in PHP (every writer would have to remember it).
- **No `declined` state.** Declining, canceling and unfriending delete the row, so the pair can start again later. `friend_request_declines` (`requester_id`, `receiver_id`, `declined_at`, unique per pair and direction) remembers only the declines, for the cooldown.
- **Indexes.** `(receiver_id, status)` and `(requester_id, status)` serve "my received/sent requests" and both sides of "my friends". MySQL silently drops the implicit index it created for a foreign key once a composite index starts with the same column, so a `down()` that removes only those composite indexes would fail with error 1553 unless it recreates the foreign key indexes first.
- **One migration.** The project was never in production, so `2025_09_26_144358_create_friendships_table.php` was moved into the module with its original name and rewritten in place to create both tables; an existing local database needs `php artisan migrate:fresh --seed`.

## Models and relations

- `Friendship` (`#[UseFactory]`, `#[UsePolicy(FriendshipPolicy::class)]`, `#[Fillable]` without the generated columns): `requester()`, `receiver()`, `isPending()`, `isAccepted()`, `involves(User)`, `otherUserId(User)` (no query; throws `InvalidArgumentException` for a user outside the row) and the scopes `involving(User)`, `between(User, User)` (through the unique pair index), `pending()` and `accepted()`.
- `FriendRequestDecline` (`#[WithoutTimestamps]`): `requester()`, `receiver()` and `activeFor(User $requester, User $receiver, int $cooldownDays)`.
- `User` gains `sentFriendRequests()` and `receivedFriendRequests()` (pending `HasMany`), `friends()`, `friendshipWith(User)`, the scope `withFriendshipCounts()` (preloads `sent_accepted_friendships_count`, `received_accepted_friendships_count` and `pending_received_friend_requests_count`) and `friendsCount()` / `pendingReceivedFriendRequestsCount()`, which reuse the preloaded values.
- **Why `friends()` joins a union.** It joins the friend ids read through the two `(<side>_id, status)` indexes (`joinSub` over a `UNION ALL`). Checked with `EXPLAIN`: an `EXISTS` with `LEAST`/`GREATEST` or an `IN … OR IN …` both scan the whole `users` table, while the join looks each friend up by primary key, so it grows with the number of friends, not with the number of users.

## Writing: `FriendshipService`

The only writer. `send()`, `accept()`, `decline()`, `cancel()` and `remove()` run in `DB::transaction` and answer a `FriendshipOperationResult` instead of throwing for business rules; an actor outside the row is a `LogicException`, because the policy already filtered it.

- **`send()`** locks the requester's and the receiver's rows together, in ascending id order (so the pending limit holds under concurrent requests and a crossed pair is serialized), refuses a suspended receiver read from that locked row (`ReceiverUnavailable`), explains an existing pair (`AlreadyFriends`, `AlreadyPending` or `IncomingRequestExists`), applies the cooldown (`CooldownActive`) and the pending limit (`PendingLimitReached`), creates the request and dispatches `FriendRequestSent`.
- **Crossed requests are refused, not accepted.** If B already asked A and A asks B, A gets `IncomingRequestExists` (409) inviting them to accept B's request from their received requests (decision of the planning).
- **The race to the unique index.** `send()` catches `UniqueConstraintViolationException` **inside** the transaction, around the insert, and reads the pair again with `FOR UPDATE`: in MySQL a duplicate undoes only that statement, and a locking read sees the row the other transaction committed. Catching it outside the transaction does not work: the rollback removes the context and the answer would be a guess.
- **Why both users, in id order (PR #82 review).** Locking only the requester deadlocked crossed requests: the insert's foreign key checks take a shared lock on the requester's *and* the receiver's rows, so A→B (holding A, waiting for B) and B→A (holding B, waiting for A) waited on each other and MySQL killed one with error 1213, which escaped as a 500 because only duplicate keys are caught. Reproduced with two concurrent processes; with both rows locked in id order the second transaction waits, sees the first row and answers `IncomingRequestExists` (a stress run of 60 crossed pairs gave 60 rows and no error). A Pest test cannot cover it: a deadlock needs two connections, and the suite runs in one transaction. The cost is that concurrent requests to the same receiver are serialized on that receiver's row.
- **The other actions** read the row again with `lockForUpdate` (the bound model can be stale) and answer `NoLongerPending` when it changed or disappeared. `decline()` upserts the decline; `cancel()` and `remove()` start no cooldown. `accept()` sets `accepted_at`.
- **Events**, dispatched inside the transaction and only for real changes: `FriendRequestSent`, `FriendRequestAccepted` and `FriendshipEnded` (`friendshipId`, `actor`, `otherUser`, and a `reason` that `FriendshipOperationResult::endsFriendship()` limits to `Declined`, `Canceled` or `Removed`; the row is already deleted, so it carries only the id). Nobody listens yet; a queued listener (notifications, SOC-85) must use `afterCommit`.

## Authorization: `FriendshipPolicy`

`create(User, User $receiver)` (never oneself, never from or to a suspended account), `accept` / `decline` (the receiver, while pending), `cancel` (the requester, while pending), `delete` (either friend, once accepted), `view` (either user of the row, or an administrator with `admin.users.friendships`), and `update`, `restore` and `forceDelete` denied explicitly. The controller applies it with `#[Authorize]`; `store` uses `#[Authorize('create', [Friendship::class, 'user'])]`, which passes the class as is and resolves `user` from the route.

The Admin panel shares this policy (SOC-87): `viewAny` requires `admin.users.friendships` and gates the user detail's Friends tab, the friendship counts of its infolist and the dashboard widget, and `deleteAny`, `restoreAny` and `forceDeleteAny` are denied. The panel has no friendship actions, so it never asks the site abilities, and the permission does not let an administrator accept, decline, cancel or remove someone else's friendship. See [Admin](admin.md).

## Endpoints

All `auth` + `verified`. The friends page and the search are Inertia pages; the actions are JSON, consumed with Inertia's `useHttp`. Each page lives in its own invokable controller, like `TrustedDeviceIndexController`: `FriendshipIndexController` (the friends page) and `FriendshipSearchController` (the people search). `FriendshipController` keeps only the actions. The search page is not the `index` because it lists people, not friendships.

| Route | Name | Throttle |
| --- | --- | --- |
| `GET friendships` (page) | `friendships.index` | `60,1,friendships.index` |
| `GET friendships/search` (page) | `friendships.search` | `60,1,friendships.search` |
| `POST friendships/{user}` | `friendships.store` | `20,1,friendships.store` |
| `POST friendships/{friendship}/accept` | `friendships.accept` | `30,1,friendships.accept` |
| `DELETE friendships/{friendship}/decline` | `friendships.decline` | `30,1,friendships.decline` |
| `DELETE friendships/{friendship}/cancel` | `friendships.cancel` | `30,1,friendships.cancel` |
| `DELETE friendships/{friendship}` | `friendships.destroy` | `30,1,friendships.destroy` |

- **Actions** answer `{result, state, friendshipId, message}`. `FriendshipOperationResult::httpStatus()` gives 200 for a change and 409 for a refusal; `state` (`FriendshipState`: `none`, `request_sent`, `request_received`, `friends`, seen by the signed-in user) is read from the pair **after** the action, so the client shows what is stored. `friendshipId` is the pair's row after the action (`null` once it is gone): with it the button can cancel right after sending, remove right after accepting, or accept the incoming request a 409 `incoming_request_exists` revealed, without reloading the page. A stranger gets 403 before anything else, a deleted row 404 and an exhausted budget 429.
- **Friends page.** `FriendshipIndexController::__invoke` renders `friendship/Friends` with `filters: {tab, q}`, `tabCounts: {friends, received, sent}` and `friendships` through `Inertia::scroll(FriendshipListItemResource::collection(…))`. `FriendshipIndexRequest` validates `tab` against `FriendshipListTab` (`friends`, `received`, `sent`; `friends` when missing, read with `tab()`) and `q` up to 50 characters (read trimmed with `term()`); its messages live in `friendship/friends.validation`. Only the active tab is queried: friends (accepted rows on either side) by `accepted_at`, received and sent requests (pending rows by `receiver_id` or `requester_id`) by `created_at`, newest first with the id as tie-breaker. Every tab leaves out the other person when suspended and filters by the start of their name with `LikePattern`; `requester.media` and `receiver.media` are preloaded, so a page runs the same queries with few or many rows. `tabCounts` counts each tab with the same base query **without** the name filter (three `count()`), so typing does not change the counters and each counter matches its list; `User::withFriendshipCounts()` is not used here because it also counts suspended people. `tabCounts` is a closure, so the infinite scroll's partial reloads skip it. `FriendshipListItemResource` serializes a row as seen by the viewer, `{friendshipId, friendshipState, since, user: {id, name, profilePicture}}` (`since` is `accepted_at` for friends and `created_at` for requests, ISO 8601; never the email), and reads only the loaded relation of the other person: a missing eager load throws `LogicException` instead of running a query per row.
- **Search page.** `FriendshipSearchController::__invoke` renders `friendship/Search` with `filters: {q}`, `searchTermMinLength` and `searchResults` through `Inertia::scroll(FriendshipSearchResultResource::collection(…))`, the same way as the notification history. `FriendshipSearchRequest` makes `q` optional and only limits it to 50 characters (a validation error above that): the term lives in the page URL, so a minimum would force a redirect back. A term shorter than `FriendshipSearchRequest::TERM_MIN_LENGTH` (2), or none, returns an empty `CursorPaginator` **without querying**; a `LIKE '%'` would list every user. The query lives in private methods of the controller (its only consumer, like the query of `TrustedDeviceIndexController`): it matches active accounts whose name starts with the term, without the viewer, escaping `\`, `%` and `_` with `App\Support\Database\LikePattern::startsWith()` so they match literally (the friends page uses the same helper), ordered by name and id, and in the same query preloads the pair's row with the viewer (through the unique pair index) and the friends in common (each side of the candidate's accepted friendships against the viewer's friend ids). `FriendshipSearchResultResource` exposes only `{id, name, profilePicture, friendshipState, friendshipId, mutualFriendsCount}` (never the email) and runs no query: a page costs the same queries with 3 or 15 results. `Inertia::scroll` adds `scrollProps.searchResults` (`pageName: "cursor"`), and `<InfiniteScroll>` asks the next page on the current URL, so `q` is kept.

## Shared props: the sidebars and the profile

- **`Props/FriendshipProps`** (`ProvidesInertiaProperties`, like `NotificationProps`), shared on every page from `HandleInertiaRequests`: `friendRequests: Inertia::defer(…)` with `{pendingCount, recent}`, where `recent` holds the 5 newest received requests (`FriendshipProps::RECENT_REQUESTS_LIMIT`) through `FriendshipListItemResource`. Requests from suspended accounts are left out of both; a guest gets `null`. Deferred, so a page renders first and the left sidebar's badge and the right sidebar's panel fill in after. Constant number of queries.
- **`Props/ProfileFriendshipProps::for(User $profileUser, User $viewer)`**, added by `ProfileController::index` and `show`: `profileFriendship: {friendsCount, isOwnProfile, friendshipState, friendshipId, mutualFriendsCount}`. `friendshipState` comes from `FriendshipState::forViewer()` over `friendshipWith()`; on the own profile it is `null`, `friendshipId` is `null` and `mutualFriendsCount` is `0`. Both counts include only accepted friendships with **active** accounts, like the friends page that the own profile's count links to; `mutualFriendsCount` is one query (the owner's active friends whose id is among the viewer's friend ids).

## Messages and configuration

- `lang/{en,es}/friendship/actions.php`: `results.<value>` for every `FriendshipOperationResult` and `validation.search_max`. The cooldown and unavailable-receiver texts are neutral on purpose (they never reveal a decline or a suspension), and `no_longer_pending` is generic because `remove()` and the race of `send()` also answer it. `lang/{en,es}/friendship/search.php` holds the texts of the search page (title, field, prompt, empty and loading states, friends in common with a plural). `lang/{en,es}/friendship/button.php` holds the friendship button (states, menu, remove dialog, accessible texts while processing, the generic error) and the profile counters (`profile.friends_count`, `profile.mutual_friends`); `HandleInertiaRequests` shares it on every page, with `home/sidebar` (the navigation and the friend requests panel). `lang/{en,es}/friendship/friends.php` holds the friends page (tabs with plural counters, filter, empty states per tab, row dates, validation), registered by its controller. The parity test of `lang/*/home/` is `SettingTranslationKeysTest`. `FriendshipTranslationKeysTest` checks parity and placeholders of every `friendship/*` catalog, one text per result and the neutral wording.
- `module.friendship`: `decline_cooldown_days` (`SOCIALHUB_FRIENDSHIP_DECLINE_COOLDOWN_DAYS`, 7), `max_pending_sent` (`SOCIALHUB_FRIENDSHIP_MAX_PENDING_SENT`, 50) `search_page_size` (15) and `list_page_size` (20, the friends page). A decline is active while `declined_at` is later than now minus the cooldown, so it is over at exactly 7 days.

## Seeding and tests

- `FriendshipSeeder` (after `AccountStatusSeeder`) gives each user 0–25 accepted friendships and 0–5 sent requests (skew 2), sometimes a decline (5%), dated over the last 60 days with `accepted_at` after the request. It builds the rows in PHP with a set of used pairs, so no pair repeats in either direction, nobody relates to themselves and a decline never shares a pair with a row; it inserts 1000 rows at a time with `insertOrIgnore`. Angel (`UserSeeder::TEST_USER_EMAIL`) first gets 5 friends, 3 received and 2 sent requests and a decline from yesterday. It does nothing when `friendships` has rows or there are fewer than two users. A full seed gives about 1 600 friendships and 300 requests.
- Tests live in `app/Modules/Friendship/Tests/{Models,Services,Policies,Crud,Security,Props,Seeders,Translations,Browser}/` (suite `Friendship`). `Crud/FriendshipIndexTest` and `Security/FriendshipIndexSecurityTest` cover the friends page (each tab and its order, the filter with literal wildcards, the exact row, suspended people, the cursor, validation, guests, other people's rows, the throttle and a constant number of queries per tab); `Props/FriendshipPropsTest` and `Props/ProfileFriendshipPropsTest` cover the shared props. The `assertInertia` tests need the page component to exist (`inertia.testing.ensure_pages_exist`). A query-count test calls the page once before measuring: the first request of a session runs one more query. The search tests assert the Inertia page (`assertInertia`, `searchResults.data`, the next page with the `cursor` from `scrollProps`) and that a short term runs no people query. `Browser/FriendshipSearchBrowserTest` (group `browser`, `composer test:browser`) types a name, scrolls until the infinite scroll loads three pages and sends a request; `Browser/FriendshipFriendsBrowserTest` accepts a request from the right sidebar (the left badge drops), removes a friend through the dialog, switches to the received tab and checks the database. `tests/Pest.php` has `createFriendRequest(?User, ?User)` and `createFriendship(?User, ?User)`. The race test inserts the crossed request from a `creating` listener and flushes the listeners afterwards.

## Frontend

`resources/js/modules/friendship/` holds both pages, the reusable button and the sidebar panel; `modules/home/` holds the navigation and `modules/profile/` the profile.

- **`components/FriendshipButton.tsx`** is the only friendship control, used by the search rows, the friends page, the right sidebar and the profile. One control per state: `none` → Add friend (`store`); `request_received` → Accept and Decline (`accept`, `decline`); `request_sent` → a menu with Cancel request (`cancel`); `friends` → a menu with Remove friend, which opens **`FriendshipRemoveDialog`** and only calls `destroy` once confirmed. It shows the new state at once (optimistic), then applies the `state` and `friendshipId` of the response; a 409 applies the server's state and shows its `message`; a 429, a network error or any other body reverts the state and shows `friendship/button.error`. Never Inertia's error modal (`onHttpException` / `onNetworkError` return `false`). It blocks clicks while a request is in flight, labels the pending action for screen readers, and calls `onChange(state, friendshipId)` so the page can reload its counters. The menus are `modal={false}`: a modal menu that opens a dialog can leave the page without pointer events. The initial state is read once per mount (give it a new `key` to reset it).
- **`Friends.tsx`** (`friendships.index`) uses shadcn `Tabs` (`shared/components/shadcn/ui/tabs.tsx`, from `radix-ui`) controlled by the committed tab, with `activationMode="manual"` so the arrow keys move the focus without a visit per tab; each trigger shows its counter, with the plural text for screen readers, and Radix mounts only the active panel. It has the name filter, an empty state per tab (or "nobody matches" when filtered, read from the committed filter) and the list. After a button action it reloads `tabCounts` and `friendRequests`, and hides the row when its new state no longer belongs to the tab (accepted or declined in Received, removed in Friends, canceled in Sent), so the list matches its counter without losing the scroll position. The hidden ids are tied to the committed tab and filter (an accepted request keeps its id and must show in Friends); when every loaded row is hidden, an effect reloads the list itself (`reset: ['friendships']`), because more pages may exist (PR #83 review). Two rows can finish an action from callbacks of the same render, so the hidden ids are updated with a functional `setState` and the empty-list check lives in that effect, not in the callback; the counter reloads are `async: true`, because a sync visit cancels the sync visit in flight and two quick actions would drop each other's counters or the list reload.
- **`hooks/useFriendsFilters.ts`** keeps `tab` and `q` in the URL (`friends` and an empty filter are left out). A tab change loads at once and cancels a pending filter load; typing is debounced. Each load uses `only: ['friendships', 'filters']` and `reset: ['friendships']`. `committedFilters` changes in `onSuccess`, so a visit cancelled by a newer one cannot commit stale filters; `pendingTab` drives a spinner on the clicked tab; `hasInteractedRef` keeps StrictMode from loading on mount.
- **`shared/components/VirtualInfiniteList.tsx`** (moved out of this module in SOC-86, also used by the home feed) is the generic list of both pages: `<InfiniteScroll data onlyNext preserveUrl>` with TanStack Virtual's `useVirtualizer` (`measureElement`, `overscan` 5), taking `data`, `items`, `getItemKey`, `renderItem`, `scrollElement`, `estimateSize`, `loadingMoreLabel` and an optional `endLabel`, shown once `usePage().scrollProps[data].nextPage` is `null` (the default slot of `<InfiniteScroll>` does not say whether a next page exists). It passes `useFlushSync: false`: otherwise the virtualizer calls `flushSync` when it measures a row while React is rendering, which React 19 reports as `flushSync was called from inside a lifecycle method` on every scroll. The list starts below the page header, so the virtualizer gets that distance as **`scrollMargin`** (measured in a `useLayoutEffect`) and each row subtracts it from its `translateY`; without it the virtualizer renders a shifted window and the last row never appears. `useVirtualizer` triggers the known `react-hooks/incompatible-library` warning.
- **`components/FriendshipListRow.tsx`** (friends page) and **`components/FriendshipSearchResultRow.tsx`** (search) show the picture, the name and `FriendshipButton`; the list row adds "friends since" (`formatFullDate`) or "sent" (`fromNow`) through `useDateTime()`, the search row the friends in common and a profile link. Both use a container query (`@container`, `@lg:`), because the central column is narrower than the window.
- **`Search.tsx`** and **`hooks/useFriendshipSearch.ts`**: a translated `InputGroup` (`name="q"`, `type="text"`; `type="search"` adds a second clear button), a prompt with the server's `searchTermMinLength`, "nobody matches", or the list; the term lives in the URL with a debounced `router.get` (`reset: ['searchResults']`) and `committedTerm` drives the empty states.
- **`components/FriendRequestsPanel.tsx`**, mounted by `modules/home/components/sidebar/HomeSidebarRight.tsx`: reads `friendRequests` through `Deferred` (skeleton meanwhile), shows up to 5 requests with Accept and Decline, an empty state, and "view all" to `friendships.index?tab=received`; after an action it calls `utils/reloadFriendshipDependentProps.ts` (SOC-85), which reloads `friendRequests` (this also updates the navigation badge) plus, in the same `router.reload`, the props of the current page (`usePage().component`) that depend on the friendship (SOC-86): `home/Home` reloads `posts` with `reset` only after an accept, so the new friend's posts appear without losing the scroll on a decline; `friendship/Friends` reloads `tabCounts` and `friendships` (with `reset`); `profile/Profile` reloads `profileFriendship`. Any other page reloads only `friendRequests`. The table lives in that helper, shared with `NotificationRealtimeListener`, which calls it when a friendship notification arrives (see [notification](notification.md)).
- **`modules/home/components/sidebar/HomeSidebarLeft.tsx`** is the app navigation (`<nav>`, items in `modules/home/data/homeSidebarNavigation.ts`: Home, Find people, Friends, Notifications, My profile). The current page's link has `aria-current="page"` (path of `usePage().url` without the query string). Friends shows `friendRequests.pendingCount` and Notifications the unread count (from the realtime notification store when initialized, otherwise the shared prop), each through `Deferred` with a skeleton, only above 0. `SharedData` (`shared/types/index.d.ts`) types `friendRequests`.
- **Profile** (`modules/profile/Profile.tsx`, types in `modules/profile/types/profileFriendship.ts`): the friend count in plural (a link to the friends page on the own profile), the friends in common and `FriendshipButton` on someone else's profile; a change reloads `profileFriendship` and `friendRequests`.
