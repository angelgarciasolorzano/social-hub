# User

Profile, account settings, account status and the authenticatable model (`app/User/`, old architecture).

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

## Backend

**User** (`app/User/`) — profile and account settings; the authenticatable model lives here.

- **AccountSettings (SOC-34)** lives in `app/User/Modules/AccountSettings/` and owns the private account-settings controller, request, input Data object, resource, last-login listener, and module tests. It uses `AccountSettingsResource`; `UserResource` remains the public-profile resource. Public profile behavior stays in `User/Profile/`, and password updates remain owned by `Auth/Modules/Password/`. The account settings page submits password changes through its dialog to the existing `PUT /setting/password` endpoint; there is no standalone password settings page or GET route. The existing `User/Profile/` and `User/Preferences/` directories are not moved.
- **User database infrastructure** lives in `app/User/Database/{Migrations,Factories,Seeders}/`; `UserServiceProvider` loads the modular migrations. The new AccountSettings migration lives there, while Laravel's initial migrations remain in the root `database/migrations/` directory. The account status (SOC-35) lives there too; see the next entry.
- **Account status (SOC-35)** — `users.status` (string cast to `App\User\Enums\AccountStatus`: `active` / `suspended`, default `active`, indexed) is the only source of truth; it never derives from `email_verified_at` or `last_login_at`, and it is not in `#[Fillable]` (mass assignment throws). Every change also writes a row of the append-only `account_status_changes` table (`App\User\Models\AccountStatusChange`, morph `account_status_change`, no `updated_at`): `user_id` (`cascadeOnDelete`), `status`, a mandatory `reason` (max `AccountStatusChange::REASON_MAX_LENGTH`, 1000) and `changed_by` (the administrator, `nullOnDelete`). `User::isSuspended()` and `User::accountStatusChanges()` (most recent first) read them. `app/User/Modules/AccountStatus/Services/AccountStatusService` is the only writer: `suspend()` / `reactivate()` (account, administrator, reason) trim the reason (`InvalidArgumentException` when blank or too long), lock the user row, throw `LogicException` if it already has the target status, write the row and the status in one transaction, revoke every trusted device on suspension through `TrustedDeviceService::revokeAll()` (reactivating does not restore them), and record `admin.account_suspended` / `admin.account_reactivated` with the row as subject and only `target_user_id` (the reason lives only in `account_status_changes`). It does not authorize: `UserPolicy::suspend` (`admin.users.suspend`, an active account that is not the administrator's own) and `UserPolicy::reactivate` (`admin.users.reactivate`, a suspended account) do, applied by the Filament actions. A suspended account cannot sign in by any path: `LoginRequest::validateCredentials()` answers `AccountStatus::SUSPENDED_LOGIN_MESSAGE` only after the password matched (a wrong password still gets `auth.failed`, and neither fires `Failed` nor counts against the throttle), which also blocks the trusted-device OTP skip; `App\Auth\Modules\Login\Requests\TwoFactorLoginRequest` extends Fortify's and is bound in its place in `FortifyServiceProvider::register()`, so an account suspended between the password and the 2FA challenge is sent back to the login before any code is checked or consumed; `User::canAccessPanel()` rejects it; and the global `App\Http\Middleware\EnsureAccountIsActive` (parameters: guard and login route) ends an open or remember-me session on the next request (403 JSON for requests that expect JSON). It is appended to the `web` group, added to the admin panel middleware as `EnsureAccountIsActive:admin,filament.admin.auth.login` right after `AuthenticateSession`, and moved ahead of authentication with `prependToPriorityList(AuthenticatesRequests::class, …)` in `bootstrap/app.php`, otherwise Filament's `Authenticate` would answer 403 through `canAccessPanel()` before the session is ended. `AccountSettingsResource` exposes `status` read-only to its owner. Tests live in `app/User/Modules/AccountStatus/Tests/` (suite `AccountStatus`) and next to the code they cover in Login, Admin and ActivityLog.
- **Account events and image upload (SOC-54)** — `app/User/Events/` holds `AccountUpdated` (only the names of the changed attributes; `AccountUpdated::fromSavedChanges($user)` builds it from `getChanges()` without `updated_at`), `AccountImageUpdated` and `AccountDeleted` (dispatched after `delete()`, with the in-memory user). `AccountSettingsController::update()` and `UserController::update()` dispatch `AccountUpdated` only when `$user->wasChanged()`; `UserController::updateImage()` dispatches `AccountImageUpdated` only after a successful upload. The image route is `POST user/image/{userImageType}` (`user.update.image`): the segment must match the controller parameter `UserImageType $userImageType` for Laravel to bind the enum, and `UserImageUpdateRequest` reads `route('userImageType')`. It used to be `{type}`, which never bound and answered 500. Its tests live in `app/User/Tests/` (suite `User`, registered in `phpunit.xml` and `tests/Pest.php`).
- Its 2FA settings feature lives in `app/User/Modules/TwoFactor/` (controller, Enums, Form Requests, recovery-code regeneration listener, and module tests); `Enums/TwoFactorStatus` (`disabled` / `pending` / `confirmed`, SOC-45) is the shared source for the `twoFactorStatus` prop. Its route remains in `app/User/routes/security.php`; `UserServiceProvider` registers `UserEventServiceProvider` for the Fortify recovery-codes listener. Auth retains its TrustedDevice listeners.

## Models

- `App\User\Models\User` — extends `Authenticatable`, implements `HasMedia`, uses `TwoFactorAuthenticatable`, has `posts()`, `comments()`, `likes()`, `trustedDeviceEvents()` (HasMany to `TrustedDeviceEvent`) and `accountStatusChanges()` (HasMany to `AccountStatusChange`, most recent first); casts `status` to `AccountStatus` and exposes `isSuspended()` (SOC-35).
- `App\User\Models\AccountStatusChange` — append-only suspension/reactivation record with its mandatory reason (SOC-35); `user()`, `changedBy()`; `UserFactory::suspended()` and `AccountStatusChangeFactory::suspended()/reactivated()/changedBy()` for tests.

## Frontend

- **AccountSettings (SOC-34)** lives in `modules/setting/modules/accountSettings/`. `AccountSettings.tsx` composes the profile form, account summary, actions, privacy overview, and static communication preferences; their typed static arrays live in `data/accountSettingsSections.ts`. Communication switches and “Ver actividad” are display-only. The public-profile link reuses its existing route, password changes open `AccountSettingsPasswordDialog` and submit to Auth's `PUT /setting/password` endpoint, and account deletion uses the existing `user.destroy` flow. There is no standalone password settings view. `AccountSettingsSummaryCard` shows 'Estado de la cuenta' as a read-only badge ('Activa' / 'Suspendida', `badgeVariants.success` / `.red`) from `accountSettings.status`, typed by `AccountStatus` in `types/accountSettings.ts` (a mirror of the backend enum, change both together).
- `AccountSettings.tsx` composes `AccountSettingsProfileForm`, `AccountSettingsSummaryCard`, `AccountActionsPanel` (which owns `AccountSettingsPasswordDialog` and `AccountSettingsDeleteDialog`, the latter confirming through `user.destroy`) and the presentational privacy and communication sections. The account status badge offers no control to change it and is never inferred from email verification, last login or the active session.
- On the backend, `AccountSettingsController` always resolves the authenticated user, and private settings data is never added to `UserResource`, which stays the public-profile serialization.
