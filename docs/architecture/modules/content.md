# Posts, comments and likes

The content modules on the new architecture: Post (`app/Modules/Post/`), Comment (`app/Modules/Comment/`) and Like (`app/Modules/Like/`), with their React modules.

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

## Post

**Post** (`app/Modules/Post/`) — posts with images via `spatie/laravel-medialibrary`. First module on the new architecture (SOC-38): `Controllers/`, `Database/{Factories,Seeders}/`, `Models/`, `Providers/`, `Requests/`, `Resources/`, `Tests/`, `routes/`; namespace `App\Modules\Post\…`.

- `App\Modules\Post\Models\Post` — implements `HasMedia` (collection `posts_images`, `singleFile()`), morph `post`. Has `user()`, `comments()` (MorphMany), `likes()` (MorphMany), the `withEngagementFor` scope and `commentsTotal()`, `likesCount()`, `isLikedBy()` (SOC-50). Resolves `PostPolicy` through `#[UsePolicy]` (SOC-57, Admin panel read access only).

## Comment

**Comment** (`app/Modules/Comment/`) — polymorphic, self-referential (comments on posts and on other comments); second module on the new architecture (SOC-40): `Controllers/`, `Database/{Migrations,Factories,Seeders}/`, `Enums/`, `Models/`, `Props/`, `Providers/`, `Requests/`, `Resources/`, `Tests/`, `routes/`; namespace `App\Modules\Comment\…`.

- **Behaviour and security rules (SOC-40, updated in SOC-46)** — the module's routes are `comments.store` (`POST comments`, `auth`+`verified`, `throttle:6,1,comments.store`), `comments.update` and `comments.destroy` (SOC-52, below), all served by `CommentController`, the module's single resource-style controller with one method per action (`store`, `update`, `destroy`); single-action controllers elsewhere stay invokable, while a module with several actions on one resource groups them in one controller (`CommentController`, `LikeController`). `store()` reads the validated input with the request's typed accessors (`string()`, `integer()`) and answers with the success flash `{type, message}`. The `throttle` third argument is a prefix because Laravel signs unnamed throttles by user only, so without it routes would share one budget. `CommentStoreRequest` and `CommentUpdateRequest` share the `NormalizesCommentContent` concern (`app/Modules/Comment/Concerns/`), which strips control characters (keeping tabs and line breaks) and trims `content` in `prepareForValidation()` before validating. Threads have a single level with a mention (SOC-41): a comment on a post can receive replies, and replying to a reply is allowed but is flattened. The client sends the comment it replied to as `commentable_id` (no extra request field); the controller attaches the new comment to the parent of the thread and stores the author of the replied reply in the nullable `replied_to_user_id` column (FK to `users`, `nullOnDelete`, so the mention disappears if that user is deleted). Replying to a post or to a root comment stores no mention. The user is derived on the server, so a forged `replied_to_user_id` in the request is ignored and a comment outside the thread can never be mentioned. `CommentResource` exposes the mention as `repliedTo: {id, name}` (or `null`) only when `repliedToUser` is loaded, and `CommentThreadProps` preloads it with `repliedToUser:id,name`, so listings keep a constant number of queries. Listings preload replies with `withCount('comments')` and `Comment::repliesCount()` reuses that `comments_count`, so serializing a page costs a constant number of queries. Regression tests live in `app/Modules/Comment/Tests/Security/`.
- **Comment persistence naming (SOC-46)** — the `comments` migration lives in `app/Modules/Comment/Database/Migrations/` and `CommentServiceProvider::boot()` registers it with `loadMigrationsFrom`, like `AuthServiceProvider` and `UserServiceProvider`. It kept its original file name on purpose: a database that already ran it keeps treating it as run, so `php artisan migrate` does not try to recreate the table. It uses `morphs('commentable')`, so the columns are `commentable_type`/`commentable_id` and the relation is `Comment::commentable()`: Laravel's `{adjective}able` convention, the same one `likes` follows with `likeable`. `model_type`/`model_id` is the convention of generic package tables (Spatie's `media` and permission tables), not of domain tables, so it was deliberately not adopted here. `create_posts_table` still lives in the global `database/migrations/` folder.
- **Comment data flow (SOC-46)** — there is no route that lists comments and no collection class. `CommentThreadProps` (`app/Modules/Comment/Props/`, an Inertia `ProvidesInertiaProperties`) is injected into `HomeController::__invoke` and `ProfileController::index/show` and exposes two props, `comments` (root comments of a post) and `replies` (replies of a comment), each `Inertia::optional(fn () => $cursorPaginator)`: they are never sent on a normal visit and only resolve on a partial reload that asks for them (`only`) with the thread in the query string, `comments_post=<id>` or `replies_comment=<id>`. Pages are `cursorPaginate(10)` with their own cursor names (`comments_cursor`, `replies_cursor`, so they do not collide with the `cursor` of `posts`), ordered by descending id for the comments of a post (newest first) and by ascending id for the replies of a comment (oldest first, so a conversation reads in order and a new reply is the last one), serialized with `->through(CommentResource)` and loaded with `user` + `withCount('comments')`. A missing or non-positive-integer id answers 404 and an unknown thread raises `ModelNotFoundException` (also 404). They return the plain paginator, not `Inertia::scroll(...)`: the hook always reloads with `reset` and keeps its own state, so the merge instruction (`mergeProps`) and scroll metadata (`scrollProps`) that `Inertia::scroll` adds to every response would be unused payload. `props.comments` and `props.replies` are the paginator envelope (`data`, `path`, `per_page`, `next_cursor`, `next_page_url`, `prev_cursor`, `prev_page_url`), pinned by `CommentThreadPropsTest`. The read budget is 60 per minute per user, enforced inside `CommentThreadProps` with `RateLimiter` under its own key (`comments.index`, separate from `comments.store`) and answers 429 with `Retry-After`. The success flash of `comments.store` is the only use of flash in the module. Tests live in `app/Modules/Comment/Tests/Props/` (`CommentThreadPropsTest`, `CommentThreadHostPagesTest`) and in `Tests/Security/` (throttle and query-count tests drive the home page with an Inertia partial-reload request).
- **Comment likes in the listing (SOC-51)** — `CommentResource` adds `likesInfo: {count, likedByMe}` (`Comment::likesCount()` and `Comment::isLikedBy(User)` reuse the preloaded `likes_count` and `liked_by_me`; for a guest `likedByMe` is false without a query). `CommentThreadProps` preloads them in the same paginated query with `withCount(['comments', 'likes'])` and `withExists(['likes as liked_by_me' => …whereBelongsTo($user)])`, so the number of queries stays constant (`CommentQueryCountTest` adds likes to the large thread).
- **Edit and delete own comments (SOC-52)** — a new migration in `app/Modules/Comment/Database/Migrations/` adds `edited_at` and `softDeletes()` to `comments` (the original migrations are untouched). `CommentPolicy` (`app/Modules/Comment/Policies/`, registered with `#[UsePolicy]` on the model) allows `update` and `delete` only to the author and never on a deleted comment; `CommentController::update()` and `destroy()` apply it with `#[Authorize('update'|'delete', 'comment')]`, which runs after route-model binding and before the FormRequest, so a stranger gets 403 even with invalid input. `PATCH comments/{comment}` (`comments.update`, `throttle:10,1,comments.update`) accepts only `content` (`CommentUpdateRequest`, required, max `Comment::CONTENT_MAX_LENGTH` (1000), same normalization as creating) and sets `edited_at = now()` only when the content changed. `DELETE comments/{comment}` (`comments.destroy`, `throttle:10,1,comments.destroy`) deletes inside a `DB::transaction`: a comment with replies is deleted logically and becomes a **tombstone** (its likes are kept but never serialized); a comment without replies is deleted for good together with its likes (`likes` has no foreign key, so `$comment->likes()->delete()` is explicit); and when the deleted one was the last reply of an already deleted parent, the parent and its likes are deleted for good too, so no empty tombstone is left. A deleted comment is always a top-level one that had replies; replies are never tombstones. Because of `SoftDeletes`, route-model binding answers 404 for a deleted comment, `Post::comments()`, `User::comments()` and the Admin panel no longer see tombstones (moderation from Admin is out of scope), and `CommentThreadProps` lists root comments with `withTrashed()` and finds the parent of a reply list with `withTrashed()` so the replies of a tombstone still load. `CommentController::store()` answers 404 when commenting directly on a tombstone but accepts a reply to a reply of a thread whose root is a tombstone (the parent is looked up with `withTrashed()`). `CommentResource` adds `editedAt`, `isDeleted` and `isMine` (the comment's author is the authenticated user; no Gate, so no extra query) and serializes a tombstone as `{id, content: null, createdAt, editedAt: null, isDeleted: true, isMine: false, user: null, repliesInfo, likesInfo: zero}`; each block of the payload lives in a private method (`author()`, `repliedTo()`, `repliesInfo()`, `likesInfo()`, `isMine()`, `tombstone()`). `[H8]` in `CommentSecurityAuditTest` now pins the exact list of `comments.*` routes. Tests live in `Tests/{Crud,Policies,Requests,Resources,Props,Security,Seeders}/`; the query-count test includes edited and deleted comments.

- `App\Modules\Comment\Models\Comment` — self-referential polymorphic via `commentable` column; casts `commentable_type` to `CommentType` (`App\Modules\Comment\Enums\CommentType`) enum. Has `user()`, `repliedToUser()` (BelongsTo via `replied_to_user_id`, the user mentioned by a reply to a reply; SOC-41), `comments()` (replies, eager-loads `user`), `likes()`, `hasReplies()`, `repliesCount()` (both reuse a preloaded `comments_count` when present), `likesCount()` and `isLikedBy(User)` (reuse `likes_count` and `liked_by_me` when preloaded; SOC-51). Since SOC-52 it uses `SoftDeletes` (`deleted_at`), has `edited_at` (immutable datetime, in `#[Fillable]`) and resolves `CommentPolicy` through `#[UsePolicy]` (application `update`/`delete` for the author, plus the Admin panel's `viewAny`/`view` since SOC-57).

## Like

**Like** (`app/Modules/Like/`) — polymorphic likes (`likes` table, morph `like`, column `likeable`) on posts and comments; third module on the new architecture (SOC-51): `Controllers/`, `Database/{Factories,Migrations,Seeders}/`, `Models/`, `Providers/`, `Tests/`, `routes/`; namespace `App\Modules\Like\…`. Comments and posts can be liked from the UI.

- **Persistence and migration (SOC-51)** — `LikeServiceProvider` (registered in `bootstrap/providers.php`) calls `loadMigrationsFrom` and registers `LikeRouteServiceProvider`. `create_likes_table` moved from the global `database/migrations/` into `app/Modules/Like/Database/Migrations/` keeping its original file name, so a database that already ran it does not run it again. A second migration adds the unique index `likes_user_id_likeable_type_likeable_id_unique` on `(user_id, likeable_type, likeable_id)`: it does not clean up repeated rows, because the module was never in production (if `migrate` fails on repeated rows in a local database, empty `likes`). `LikeFactory` is complete (`user_id`, and a Post as the default likeable; use `->for($comment, 'likeable')`); the `createLike(?User, Post|Comment|null)` helper lives in `tests/Pest.php`.
- **Toggle endpoint (SOC-51)** — `POST comments/{comment}/like` (`comments.like`, `toggleComment`) and `POST posts/{post}/like` (`posts.like`, `togglePost`), both `auth`+`verified` with `throttle:30,1,<route name>` (each its own budget, separate from `comments.store`), are served by `LikeController`, which shares a private `toggle()` between both actions (SOC-50), and answer JSON `{liked: bool, likesCount: int}`: it is the only JSON route and it is consumed with Inertia v3's `useHttp`, a standalone request that does not trigger a page visit and does not depend on the host page, so Home and Profile share it. Any authenticated user can like any comment, including replies and their own; there is no visibility rule because posts and comments have none (add a policy if private posts ever exist). The unique index settles a double click or two tabs: a `UniqueConstraintViolationException` while creating counts as "already liked". `verified` filters nobody today because `User` does not implement `MustVerifyEmail`, in every route of the project.
- **Real counts and likes of posts (SOC-50)** — `Post::withEngagementFor(User)` (an Eloquent `#[Scope]`) loads, in the same query that lists posts, `root_comments_count` (live root comments, tombstones excluded), `replies_count` (replies to any root comment, including the ones of a tombstone, through a correlated subquery that uses `withTrashed()`), `likes_count` and `liked_by_me`, so listing posts keeps a constant number of queries. `Post::commentsTotal()` is their sum (it queries only when the counters are not preloaded), `likesCount()` and `isLikedBy(User)` follow the same pattern as `Comment`. `HomeController` and `ProfileController::index/show` use the scope; `PostResource` adds `commentsCount`, `likesInfo: {count, likedByMe}` and `user: {id, name, profilePicture}|null` (the post's own author, never the email; listings preload `user.media`), so `PostCard`, `PostDetail` and `CommentDialog` read the author from the post instead of receiving the page's user: Home lists posts of any user today and a friends/interests feed only has to change its query. `PostCard` now shows these real numbers and a working like button; they used to be fixed text.
- **Seeding (SOC-51)** — `LikeSeeder` (after `CommentSeeder` in `DatabaseSeeder`) gives each comment 0–8 likes (skew 3) from distinct random users, inserted per chunk with `insertOrIgnore` so running it twice does not repeat likes. Tests live in `app/Modules/Like/Tests/{Models,Crud,Security,Seeders}/`.

- `App\Modules\Like\Models\Like` — polymorphic via `likeable`, morph `like` (moved out of the old architecture in SOC-51); `user()`, `likeable()`.

## Frontend

- **Comments (SOC-46)** lives in `modules/comment/` (singular, like the backend module): `components/` (`CommentList`, `CommentItem`, `CommentRepliesList`, `CommentLoadStates`, plus `dialog/` with `CommentDialog` and `CommentInputDialog`, and `forms/`), `enums/commentType.ts` (`CommentType` and `CommentTypeValues`, same `post`/`comment` values as the backend enum), `hooks/` (`useCommentPaginated`, `useCommentScrollAreaViewport`) and `types/`; the public entry is `@/modules/comment`. `useCommentPaginated(commentableType, commentableId)` loads, pages and refreshes one thread: every request is `router.reload` on the host page with the target explicit in the data (`comments_post` / `replies_comment` + cursor), `only: [propName]`, `preserveUrl: true`, `replace: true` and `reset: [propName]` (`propName` is `comments` or `replies`, never both: asking for both would resolve both props and 404 the one without its thread parameter), so the browser URL never changes and nothing depends on the current query string. It copies the page from `onSuccess` into local state and merges pages without repeating ids (a next page goes after what is loaded; a refresh goes before it and keeps the rest only when everything was already loaded). `onHttpException`/`onNetworkError` return `false`, so a 404/429 does not open Inertia's error modal; the hook exposes `loadFailure` (`"refresh" | "more"`) and `retryLoad()`, and `loadMoreComments()` stops auto-loading while a failure is pending to avoid a request loop. The target is fixed per mount (`CommentList` per post, `CommentRepliesList` per comment). **Replies to replies (SOC-41):** `CommentItem` with `isReply` keeps the "Responder" button (title "Responder a {name}", it sends the reply's own id and the server flattens it to the parent), shows "Respondiendo a @name" when `comment.repliedTo` is set, and renders neither "Mostrar N respuestas" nor a nested `CommentRepliesList`; after publishing it refreshes the parent's list through the inherited `uploadedComments`. `CommentForm` shows `errors.commentable_id` and, through `onHttpException`/`onNetworkError` returning `false`, a local message for server errors such as 429. `CommentLoadStates.tsx` holds the shared skeleton and error-with-retry blocks. **`<InfiniteScroll>` was tried and discarded**: it works in the dialog (its `params` prop can carry the thread), but it renders from page props, throws if the optional prop has no scroll metadata yet, and its refresh (`reset`) drops already-loaded pages, so publishing with 12 comments loaded left only 10 until scrolling again.
- **Likes and character counter (SOC-51, SOC-50)** — `shared/types/likes.ts` defines `LikesInfo` `{count, likedByMe}` and `LikeToggleResponse` `{liked, likesCount}`; `types/comment.ts` and `types/post.ts` use `likesInfo: LikesInfo`. `shared/hooks/useLikeToggle(toggleUrl, initialLikesInfo)` wraps Inertia v3's `useHttp` against the Wayfinder URL of `LikeController::toggleComment` or `togglePost`: it updates the count and `likedByMe` at once through the `optimistic` option (reverted automatically if the request fails), replaces them with the server's `{liked, likesCount}` on success, ignores clicks while a request is pending, and turns 429 and network failures into a Spanish message through `onHttpException`/`onNetworkError` returning `false` (no Inertia error modal). It reads the initial values once per mount and does not resync when the list reloads. `components/CommentLikeButton.tsx` and `modules/post/components/PostLikeButton.tsx` render it with `Heart` (filled when liked), `aria-pressed`, `disabled` while pending and the error in a `role="alert"` span; `PostCard` owns the hook so the likes count and the button share state, and keeps `commentsCount` in local state that `CommentList` adjusts through `onCommentsCountChange(delta)` (+1 when a comment or reply is published, −1 when one is deleted, editing changes nothing). `shared/components/form/CharacterCounter` shows "n / max caracteres" (amber from 90% with `text-amber-700 dark:text-amber-500`, destructive above the limit; `app.css` defines no `warning` token, `blatui.css` is only loaded for Livewire, so `text-warning` would generate nothing); the comment form, the reply dialog and `CommentEditDialog` use it with `COMMENT_CONTENT_MAX_LENGTH` in `modules/comment/constants/commentContent.ts`, a frontend mirror of `Comment::CONTENT_MAX_LENGTH` that is not sent through props, so **both must be changed together**. The textarea has no `maxLength` (pasting is not truncated); the submit button is disabled above the limit. For the replies list, `useCommentPaginated.uploadedComments(afterReload?)` loads every page to the end (accumulating them and replacing the state once, so the list does not flicker) and `CommentRepliesList` then scrolls the viewport to the new reply; the comments of a post keep refreshing only the first page. There are no frontend tests: it is checked with `npm run types`, ESLint, Prettier and the browser.
- **Edit and delete (SOC-52)** — `types/comment.ts` adds `Comment.editedAt`, `isMine` and `isDeleted`, and `content` and `user` can be `null` for a tombstone (`CommentFormData` has its own `content: string`). `components/CommentActionsMenu.tsx` (shadcn `DropdownMenu`, icon trigger with `aria-label`) shows Editar and Eliminar only when `isMine` and the comment is not deleted, and opens `dialog/CommentEditDialog.tsx` (a `PATCH` through `useForm` and the Wayfinder `update` action, with the form mounted only while open so each opening starts from the current text) and `dialog/CommentDeleteDialog.tsx` (the existing `Dialog`, no `alert-dialog` dependency; `DELETE` through `useForm` and the Wayfinder `destroy` action). Both turn 429 and network failures into a local message through `onHttpException`/`onNetworkError` returning `false`. `CommentItem` is split into `LiveCommentItem` (menu, "· editado" with the full date in `title`) and `DeletedCommentItem` ("Comentario eliminado", no menu, likes or reply button, but "Mostrar N respuestas" still works), chosen by the `isLiveComment` type guard. `useCommentPaginated` gained `updateCommentContent(commentId, content)` (patches the loaded list after an edit, marking `editedAt` only if the text changed) and `reloadComments()` (replaces the list with the first page after a delete, because the merge of `uploadedComments` would keep a comment that no longer exists); deleting a reply also reloads the root list so the replies count and a vanished parent tombstone are right.
- **Comments UI uses the project's shadcn components (SOC-46)** — `Button` (`ghost`, `xs`) for the actions of `CommentItem`, `Card` (overridden to `gap-0 py-0 rounded-md bg-muted/50 shadow-none`; replies use `border-0 bg-transparent`), `Alert` (`destructive`) in `CommentLoadError`, `Spinner` for the "loading more" rows, `Skeleton`, and `ScrollArea` for every scroll container (post pane, input-dialog body, comment list, replies list). The module has no native `<button>`, no `overflow-*` scroll container and no hard-coded gray/hex color; colors come from theme tokens (`text-muted-foreground`, `bg-muted/50`, the default `border`). `ScrollArea` caveats: its Root does not shrink inside a flex column (use `min-h-0 flex-1`); a height cap must go on the viewport (`[&>[data-slot=scroll-area-viewport]]:max-h-72`), not on the Root; and the pagination `IntersectionObserver` must use the viewport as its root, which `useCommentScrollAreaViewport` returns from a ref on the Root without editing `shadcn/ui`. `Alert` brings `w-full`, so `CommentLoadError` overrides it with `w-auto` because the replies list renders it with a left margin. To check light mode, emulate `prefers-color-scheme`: the app follows the system theme (`appearance=system`), so toggling the `dark` class is not enough.
