# Real-time notification center

The React notification center (SOC-68): domain subscribers, Laravel notifications, the private broadcast channel and the history page.

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

**Notification** (`app/Modules/Notification/`) — application notification center for React (SOC-68): domain subscribers, Laravel notifications, the private broadcast channel, the Inertia history page and its authenticated endpoints. Its delivery and storage boundaries are described below; it does not replace the Filament panel's notification UI.

`app/Modules/Notification/` owns the React notification center. `NotificationServiceProvider` registers the module routes and subscribes `CommentNotificationSubscriber` to `CommentCreated` and `LikeNotificationSubscriber` to `LikeToggled`. The subscribers resolve recipients on the server and ignore actions by the recipient: a root comment notifies the post owner; a reply to a root comment notifies that comment's author; a reply to a reply uses `replied_to_user_id`. A like on a post or comment notifies that content's author.

- **Routes.** `notifications.index` (`GET /notifications`, the Inertia history with cursor pagination ordered by creation date and id), `notifications.recent` (`GET /notifications/recent`, up to five rows), `notifications.read` (`POST /notifications/{notificationId}/read`) and `notifications.read-all` (`POST /notifications/read-all`), served by `NotificationController`; the writes are `throttle:30,1,<route name>`, and every query and change goes through the authenticated user's notifications relation.
- **Notification classes.** `CommentedOnPostNotification` and `RepliedToCommentNotification` (`app/Modules/Notification/Notifications/`) carry comments and replies; `LikeNotification` broadcasts like groups. The database keeps the history; the broadcast is the live transport, not the source of truth. The stored summary survives the deletion of the original content, so opening its target can still answer 404.
- **Grouped likes.** `LikeNotificationGroupService` keeps one unread row per recipient and post/comment destination in Laravel's `notifications` table. It serializes changes by locking the liked content and the unread group, stores unique actor id/name snapshots, updates a group's existing notification id, and broadcasts after commit. Removing the final actor deletes an unread group; a later like creates a new unread group. A read group remains history and is not reopened.
- **Payload and language.** The React resource exposes only `{id, type, summary, actors, target, readAt, createdAt}`. Actor snapshots contain only id and name; targets contain post/comment ids. Comment text, email and full model data are not stored in this payload. Comment and reply summaries use the recipient's preferred locale; grouped-like summaries are regenerated when the actor group changes. UI text comes from `lang/{en,es}/notification/center.php`.
- **Supported types.** `NotificationType` is the PHP source of truth for `comment_on_post`, `comment_reply` and `likes_grouped`; emitters and the likes group service use its cases. The React type is derived from a closed TypeScript tuple with a runtime guard. History, recent notifications, read actions and the deferred unread count filter with `NotificationType::values()`; Echo payloads with unknown types are discarded before Zustand or Sonner, and only a `likes_grouped` deletion removes a group.
- **Delivery.** Comment and reply notifications implement `ShouldQueue` and use Laravel's `database` and `broadcast` channels. Like groups are written by the group service and their broadcast is requested in `DB::afterCommit`. `.env.example` selects `BROADCAST_CONNECTION=reverb` and `QUEUE_CONNECTION=database`; Reverb transports private-channel events and `queue:listen` processes queued work. `composer run dev` also starts `reverb:start` with Laravel's `serve`, queue listener, Pail and Vite processes. No email or browser push is sent.
- **Private channel and HTTP.** `User::receivesBroadcastNotificationsOn()` names `users.{id}.notifications`; `app/Modules/Notification/routes/channels.php` authorizes only the same signed-in user while the account is active, and the root `routes/channels.php` loads that module file. `GET /notifications` filters supported types before cursor pagination, `GET /notifications/recent` filters before its five-row limit, and the two POST actions operate only on supported types. Marking an owned unsupported notification returns 404; mark-all changes only unread supported rows. Routes use the web session with `auth` and `verified`; writes are throttled. `NotificationProps` shares a deferred unread count filtered to the same types through Inertia.
- **Filament boundary.** The Admin approval flow still creates Filament database notifications and Filament still owns their panel UI and polling; SOC-68 does not change that emitter or flow. Both flows share Laravel's existing `notifications` table. The React queries and Echo listener isolate the center by supported type, while Filament notifications continue to work in the panel.
- **React integration.** `resources/js/app/app.tsx` configures Echo with the `VITE_REVERB_*` variables and mounts `NotificationRealtimeListener` once for the application. It subscribes through `useEchoNotification`, updates the user-scoped Zustand store and sends new/changed notification summaries to the existing Sonner toaster. The bell fetches recent rows on open; the history page uses Inertia cursor scrolling and both views can mark rows read. `Home`, `Profile`, `Post` and notification-history responses register `notification/center` so the shared header has its translations. System announcements remain page-load props, not part of this real-time flow.
