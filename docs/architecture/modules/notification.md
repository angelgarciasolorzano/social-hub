# Real-time notification center

The React notification center (SOC-68): domain subscribers, Laravel notifications, the private broadcast channel and the history page.

> Moved from `CLAUDE.md` (SOC-78). Keep this document in sync with the code: update it in the same PR as any change to the module. `CLAUDE.md` keeps only the short orientation and the invariants that break things.

**Notification** (`app/Modules/Notification/`) — application notification center for React (SOC-68): domain subscribers, Laravel notifications, the private broadcast channel, the Inertia history page and its authenticated endpoints. Its delivery and storage boundaries are described below; it does not replace the Filament panel's notification UI.

`app/Modules/Notification/` owns the React notification center. `NotificationServiceProvider` registers the module routes and subscribes `CommentNotificationSubscriber` to `CommentCreated` `LikeNotificationSubscriber` to `LikeToggled` and `FriendshipNotificationSubscriber` to the friendship events (SOC-85). The subscribers resolve recipients on the server and ignore actions by the recipient: a root comment notifies the post owner; a reply to a root comment notifies that comment's author; a reply to a reply uses `replied_to_user_id`. A like on a post or comment notifies that content's author. A sent friend request notifies its receiver and an accepted one notifies its requester.

- **Routes.** `notifications.index` (`GET /notifications`, the Inertia history with cursor pagination ordered by creation date and id), `notifications.recent` (`GET /notifications/recent`, up to five rows), `notifications.read` (`POST /notifications/{notificationId}/read`) and `notifications.read-all` (`POST /notifications/read-all`), served by `NotificationController`; the writes are `throttle:30,1,<route name>`, and every query and change goes through the authenticated user's notifications relation.
- **Notification classes.** `CommentedOnPostNotification` and `RepliedToCommentNotification` (`app/Modules/Notification/Notifications/`) carry comments and replies; `LikeNotification` broadcasts like groups; `FriendRequestReceivedNotification` and `FriendRequestAcceptedNotification` carry friend requests (SOC-85). The database keeps the history; the broadcast is the live transport, not the source of truth. The stored summary survives the deletion of the original content, so opening its target can still answer 404.
- **Grouped likes.** `LikeNotificationGroupService` keeps one unread row per recipient and post/comment destination in Laravel's `notifications` table. It serializes changes by locking the liked content and the unread group, stores unique actor id/name snapshots, updates a group's existing notification id, and broadcasts after commit. Removing the final actor deletes an unread group; a later like creates a new unread group. A read group remains history and is not reopened.
- **Friend requests (SOC-85).** `FriendshipNotificationSubscriber` listens to `FriendRequestSent` (notifies the receiver), `FriendRequestAccepted` (notifies the requester) and `FriendshipEnded`. The friendship events are dispatched inside `FriendshipService`'s transaction and the queue has `after_commit` off, so both classes call `afterCommit()` in their constructor: a rolled back action sends nothing. Before delivery, `shouldSend()` reads the friendship again: the received one is sent only while the request is still pending and addressed to that user, the accepted one only while the friendship is still accepted with that user as requester, and neither to a suspended account. Their data is the usual `{summary, actors, target}` with `target.postId` and `target.commentId` set to `null` plus `target.friendshipId`, kept only to find the row later; `NotificationResource` drops it from the public contract.
- **Removing a stale request.** When a request is accepted, declined or canceled, the subscriber deletes the receiver's **unread** `friend_request_received` row whose `data->target->friendshipId` matches, inside the service's transaction, and sends `FriendRequestReceivedNotification::deletion($id)`, a broadcast-only `{deleted: true}` with that id (also after commit). A read row stays as history: the client subtracts one unread per deletion, so deleting a read row would lower the counter twice. Removing a friendship deletes nothing; declines, cancellations and removals are not notified, only recorded in the activity log.
- **Payload and language.** The React resource exposes only `{id, type, summary, actors, target, readAt, createdAt}`. Actor snapshots contain only id and name; targets contain post/comment ids (plus the friendship id of a friend request, never exposed). Comment text, email and full model data are not stored in this payload. Comment and reply summaries use the recipient's preferred locale; grouped-like summaries are regenerated when the actor group changes. UI text comes from `lang/{en,es}/notification/center.php`.
- **Supported types.** `NotificationType` is the PHP source of truth for `comment_on_post`, `comment_reply`, `likes_grouped`, `friend_request_received` and `friend_request_accepted`; emitters and the likes group service use its cases. The React type is derived from a closed TypeScript tuple with a runtime guard. History, recent notifications, read actions and the deferred unread count filter with `NotificationType::values()`; Echo payloads with unknown types are discarded before Zustand or Sonner, and only a `deleted` marker of `likes_grouped` or `friend_request_received` removes a row.
- **Delivery.** Comment, reply and friend request notifications implement `ShouldQueue` and use Laravel's `database` and `broadcast` channels. Like groups are written by the group service and their broadcast is requested in `DB::afterCommit`. `.env.example` selects `BROADCAST_CONNECTION=reverb` and `QUEUE_CONNECTION=database`; Reverb transports private-channel events and `queue:listen` processes queued work. `composer run dev` also starts `reverb:start` with Laravel's `serve`, queue listener, Pail and Vite processes. No email or browser push is sent.
- **Private channel and HTTP.** `User::receivesBroadcastNotificationsOn()` names `users.{id}.notifications`; `app/Modules/Notification/routes/channels.php` authorizes only the same signed-in user while the account is active, and the root `routes/channels.php` loads that module file. `GET /notifications` filters supported types before cursor pagination, `GET /notifications/recent` filters before its five-row limit, and the two POST actions operate only on supported types. Marking an owned unsupported notification returns 404; mark-all changes only unread supported rows. Routes use the web session with `auth` and `verified`; writes are throttled. `NotificationProps` shares a deferred unread count filtered to the same types through Inertia.
- **Filament boundary.** The Admin approval flow still creates Filament database notifications and Filament still owns their panel UI and polling; SOC-68 does not change that emitter or flow. Both flows share Laravel's existing `notifications` table. The React queries and Echo listener isolate the center by supported type, while Filament notifications continue to work in the panel.
- **React integration.** `resources/js/app/app.tsx` configures Echo with the `VITE_REVERB_*` variables and mounts `NotificationRealtimeListener` once for the application. It subscribes through `useEchoNotification`, updates the user-scoped Zustand store and sends new/changed notification summaries to the existing Sonner toaster. The bell fetches recent rows on open; the history page uses Inertia cursor scrolling and both views can mark rows read. `Home`, `Profile`, `Post` and notification-history responses register `notification/center` so the shared header has its translations. System announcements remain page-load props, not part of this real-time flow.

## Frontend

The UI lives in `resources/js/modules/notification/`: `Notifications.tsx` (the history page), `NotificationListItem.tsx` (one row), `NotificationDropdown.tsx` (the header bell) and `NotificationRealtimeListener.tsx` (global reception). `types/notification.ts` derives `NotificationType` from the closed tuple `comment_on_post`, `comment_reply`, `likes_grouped`, `friend_request_received`, `friend_request_accepted`, a mirror of the PHP enum. Each row keeps the summary, the actor and target snapshots and the read state.

- **Global connection.** `app.tsx` configures Echo with `VITE_REVERB_APP_KEY`, `VITE_REVERB_HOST`, `VITE_REVERB_PORT` and `VITE_REVERB_SCHEME`. `NotificationRealtimeListener` is mounted once in `withApp`, reads the initial props and follows Inertia's `navigate` events to detect session or user changes and the deferred counter. For an active session `useEchoNotification` listens on the private channel `users.{id}.notifications` (the server authorizes the subscription); the listener inserts or updates the row in Zustand and Sonner shows a toast only when the received state changes.
- **Runtime type boundary.** `isNotificationType` validates the broadcast `type` before the listener touches Zustand or shows a toast; an unknown type is discarded, deletion payloads included. Only a `deleted` marker of `likes_grouped` or `friend_request_received` removes its row.
- **Friendship refresh (SOC-85).** The listener keeps the open page's component in a ref (the initial `page.component` from `app.tsx`, then each `navigate` event). When a friendship notification arrives it calls `reloadFriendshipDependentProps` (`modules/friendship/utils/`) with that component and the new state (`friends` for an accepted request), so the sidebar's friend requests, the navigation badge and the props of the open page reload in one request; a deletion reloads them with `none`, so the feed is not reloaded. Comment and like notifications reload nothing.
- **State and deduplication.** `stores/notificationStore.ts` keeps the current authenticated user, the unread counter and the notifications received through Echo, keyed by Laravel's id: a repeated broadcast never duplicates a row and a likes update changes the existing group. Switching users clears the previous state; the Inertia counter seeds it while the deferred prop resolves. A selector of `useNotificationStore` must never return a new array or object: Zustand reads it through `useSyncExternalStore`, which compares snapshots with `===`, so a fresh `[]` for a store that is not yet the current user's (right after signing in) re-renders forever (`Maximum update depth exceeded`, SOC-86). `useNotificationDropdown` and `useNotificationHistory` return the module constant `EMPTY_NOTIFICATIONS` instead; `undefined` and `null` are safe. `LoginBrowserTest` signs in through the form and checks `/home` renders without JavaScript errors.
- **Bell and history.** `NotificationDropdown` requests `notifications.recent` when it opens, merges it with the live rows, links to the history and marks a row read before opening its link. `Notifications.tsx` loads `/notifications` as an Inertia page with per-row and mark-all actions and paginates with `<InfiniteScroll>`. HTTP actions use `useHttp` and Wayfinder helpers.
- **Links and icons (SOC-85).** `utils/notificationUrl.ts` (`getNotificationLink`) is the only place that turns a notification into its page and action label: comments and likes open `posts.show` with the comment thread, `friend_request_received` opens `friendships.index?tab=received` and `friend_request_accepted` the profile of `actors[0]`; without a post or an actor there is no link. The history row uses it and the bell's `getNotificationUrl` wraps it. `NotificationTypeIcon` shows one lucide icon per type in both views, named for screen readers by `notification/center.types.<type>`; its `Record<NotificationType, …>` map fails to compile when a type has no icon.
- **Texts and dates.** Components use `useTranslation()` and `useDateTime()` with `lang/{en,es}/notification/center.php`.
- **Filament boundary.** Filament notifications never enter the React center or become application broadcasts; system announcements do not use this channel either.
- **Checking.** There is no React test suite: changes are checked with `npm run types`, ESLint, Prettier and `npm run build:ssr`, plus a manual check with two sessions (private channel, live reception, grouping, toasts, read state and the friendship refresh). `app/Modules/Notification/Tests/Browser/FriendshipNotificationsBrowserTest.php` covers the history link of a received request and its removal after a cancel; browser tests do not run Reverb, so the live refresh is checked by hand.
