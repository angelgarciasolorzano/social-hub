# Auditoría de las suites de Auth y User (TASK-007)

Alcance: los 46 archivos de las suites Login, Register, Email, Password, TrustedDevice, TwoFactor, AccountSettings, AccountStatus y User (unos 390 casos). Mismo criterio que en las auditorías anteriores: solo se elimina un caso cuando otro detecta exactamente el mismo fallo y se cita cuál; no se fusionan comportamientos distintos.

Esta suite tiene una regla de diseño que limita lo que se puede quitar: SOC-45 exige comprobar la 2FA **dos veces** a propósito, en el FormRequest (`RequiresTwoFactorOtp`) y otra vez en el servicio con la fila bloqueada. Los tests de las dos capas parecen duplicados pero protegen defensas distintas, y se conservan (ver C1).

## Setup a corregir o simplificar

- **S1 — Códigos "equivocados" que pueden ser el correcto.** Varios tests usan `'000000'` como código inválido con un usuario que tiene un secreto TOTP real (`createUserWithTwoFactor()`), y aceptan que el código sea rechazado. Con probabilidad de 1 en un millón por ejecución, `'000000'` es el código válido de ese momento y el test falla. Sumando todos los casos, es un fallo intermitente posible cada pocas decenas de miles de ejecuciones (más probable con la suite en paralelo y en CI). `TrustedDeviceReactivateTest` ya lo resuelve en un test (`$wrongOtp = $validOtp === '000000' ? '000001' : '000000'`). Propuesta: un helper `invalidOtpFor(User $user): string` en `tests/Pest.php`, junto a `validOtpFor()`, usado en `Crud/TrustedDeviceStoreTest.php`, `Lifecycle/TrustedDeviceRenewTest.php`, `Lifecycle/TrustedDeviceReactivateTest.php`, `Lifecycle/TrustedDeviceCodeThrottleTest.php`, `Listeners/TrustedDeviceInvalidateTest.php`, `Services/TrustedDeviceServiceTest.php`, `Services/TwoFactorCodeVerifierTest.php` y `app/Modules/ActivityLog/Tests/Listeners/TwoFactorActivityTest.php`. Los `'123456'` enviados por usuarios **sin** secreto no fallan nunca y se dejan. 8 archivos más `tests/Pest.php`.
- **S2 — Claves de caché escritas a mano.** `Queries/TrustedDeviceDashboardCacheTest.php` arma 8 veces `'trusted-device:dashboard:'.$user->id.':stats'` (y `:recent-activity`), aunque `tests/Pest.php` ya ofrece `trustedDeviceStatsCacheKey()` y `trustedDeviceRecentActivityCacheKey()`, que usan los demás archivos. Si la clave cambia, ese archivo es el único que se rompe por motivos de redacción. 1 archivo.
- **S3 — El test del valor por defecto no prueba el valor por defecto.** `AccountStatusMigrationTest.php` · "creates new accounts as active when no status is given" crea el usuario con `createUser()`, y la factory **sí** da el status. Debe insertar una fila sin `status` (con `DB::table('users')->insert()` o `forceCreate()` sin ese campo) para fijar el `default('active')` de la columna. Es una corrección de cobertura, no una eliminación; habilita R7. 1 archivo.

## Revisado y conservado

- **C1 — Defensa en dos capas de SOC-45**: los tests de 2FA desactivada o pendiente en `TrustedDeviceStoreTest` y `TrustedDeviceRenewTest` (FormRequest) y los equivalentes de `TrustedDeviceServiceTest` ("rejects registering/renewing a device when two-factor is disabled or pending" y las variantes "… after the user model was loaded"). Cada capa puede fallar por separado y CLAUDE.md las exige a las dos.
- **C2 — Códigos de recuperación por endpoint**: "rejects a recovery code that belongs to another user" en reactivar y en desactivar 2FA, y "does not accept the same recovery code to reactivate a second device", repiten reglas del verificador, pero son el límite de seguridad de cada endpoint (qué usuario le pasa el controlador al verificador). Se conservan por la regla de no tocar límites de seguridad salvo duplicación exacta.
- **C3 — Mensaje fijo sin eco del código** en store, renew y reactivate: tres endpoints, tres mensajes.
- **C4 — Saltarse el OTP con la cookie** (`TrustedDeviceOtpBypassTest`) y cuentas suspendidas (`SuspendedAccountLoginTest`, `SuspendedAccountTwoFactorChallengeTest`, `EnsureAccountIsActiveTest`): cada camino de entrada (contraseña, cookie, challenge, sesión abierta, remember-me, JSON) es distinto.
- **C5 — Presupuesto compartido de códigos** (`TrustedDeviceCodeThrottleTest`): el dataset recorre las cuatro rutas a propósito, porque cada una debe tener el throttle.
- **C6 — `TrustedDeviceDashboardCacheTest` · "invalidates dashboard cache after every successful trusted device mutation"**: es un test de integración que recorre todas las rutas y vuelve a calcular las estadísticas; se superpone con los tests del servicio, pero es el único que prueba que el controlador usa el servicio en cada ruta y que el valor recalculado es correcto. Lo que se le pide es S2, no eliminarlo.
- **C7 — Seeders y factories** (`TrustedDeviceSeederTest`, `TrustedDeviceFactoryTest`, `UserSeederTwoFactorTest`, `UserFactoryTwoFactorStatesTest`, `AccountStatusSeederTest`): cada propiedad puede fallar por separado.
- **C8 — Register, Email, Password, AccountSettings y User**: sin duplicados entre capas. `AccountSettingsSummaryTest` tiene dos tests de campos ausentes en `UserResource` (privados y status), sobre campos distintos.
